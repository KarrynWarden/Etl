# Локальный airflow на dev-PC (Фаза 1)

Лёгкий airflow прямо на рабочем ПК для экспериментов: правишь даги/код в VS Code —
airflow видит изменения сразу, без копирования. Запуск одной командой, остановка
по Ctrl-C, все файлы видны в обычном проводнике.

- **Без Docker.** Берём готовый venv с сервера → точный паритет с продом (airflow
  2.7.2, Python 3.10, cx_Oracle 8.3.0, psycopg2 2.9.9), и никакой возни с контейнерами.
- **Лёгкий режим:** SQLite + SequentialExecutor, без Postgres/Redis.
- **Изоляция:** на прод/тест-сервер это не влияет никак.

Предпосылки: dev-PC и сервер — Astra 1.7 x86-64 (совпадают), свободно ~2 ГБ на диске,
dev-PC достаёт боевые БД по сети.

> **Важно про Astra SE и /opt.** Запись в `/opt` закрыта даже для `root`
> (мандатный контроль). Поэтому runtime распаковываем **в домашнюю папку**
> (`~/airflow-runtime`), без `sudo`, и перенастраиваем venv на новое место.

---

## Шаг 1. Упаковать runtime на сервере

```bash
ssh devel@airflow
sudo -s
# скопируй на сервер local/pack-runtime.sh (или выполни команды из него):
bash pack-runtime.sh
```

Получится `~/airflow-runtime-ГГГГММДД.tar.gz` в домашней папке `devel`.

## Шаг 2. Перенести и распаковать на dev-PC (без sudo)

```bash
scp devel@airflow:/home/devel/airflow-runtime-*.tar.gz ~/
mkdir -p ~/airflow-runtime
tar xzf ~/airflow-runtime-*.tar.gz -C ~/airflow-runtime
ls -ld ~/airflow-runtime/opt/python3.10 ~/airflow-runtime/opt/airflow/venv ~/airflow-runtime/opt/oracle
```

Должны появиться все три папки внутри `~/airflow-runtime/opt/`.

## Шаг 3. Перенастроить venv на новое место

venv помнит старый путь `/opt/...` — перенацелим его:

```bash
bash local/relocate-venv.sh ~/airflow-runtime
```

Скрипт поправит симлинки, `pyvenv.cfg` и шебанги и в конце проверит:
```
Python 3.10.7
2.7.2
OK: venv работает из ...
```

## Шаг 4. Запустить локальный airflow

Из корня репозитория:
```bash
bash local/airflow-local.sh
```

При первом запуске airflow сам создаст БД и напечатает логин/пароль для UI.
Открой <http://localhost:8080>. Остановка — Ctrl-C.

Что делает скрипт:
- `AIRFLOW_HOME = ~/airflow-local` (рантайм airflow, **вне** репозитория);
- даги берутся из `dags/` этого репозитория, код — из `Functions/`, `Src/`, `Connect/`
  (через `PYTHONPATH`);
- `ETL_MODE=""`, `ETL_FULL_PATH=<корень репо>/` → конфиг читается из `etlFolder/`
  (dev-версия, не Prod);
- airflow вызывается через интерпретатор venv напрямую, без зависимости от шебангов.

Главное на этом шаге: **venv с сервера завёлся и DAG-и парсятся** — в UI не должно
быть красных ошибок импорта. Для парсинга и UI пароли к БД не нужны (подключения
происходят только при запуске задачи).

## Шаг 5 (опционально). Реальные запуски задач против БД

Чтобы запускать задачи (а не только смотреть, как даги парсятся), нужны реквизиты БД.
Скопируй шаблон и впиши реальные значения — файл `.env` в `.gitignore`:
```bash
cp .env.example .env
# отредактируй .env: ETL_ORACLE_*, ETL_POST_*
```

> Сейчас `Connect/__init__.py` берёт реквизиты из захардкоженных заглушек, а не из
> переменных окружения (ветки с `os.environ` закомментированы), и путь к Oracle-конфигу
> там прибит к `/opt/oracle/config` — которого на dev-PC нет (runtime в домашней папке).
> Чтобы `.env` и локальный Oracle заработали, эти места нужно перевести на переменные
> окружения — отдельный небольшой шаг, делаем после того, как airflow поднимется и
> даги станут парситься.

## Если что-то не так

- **`mkdir /opt/...: Отказано в доступе` даже под root** — это Astra SE, так и должно
  быть. Не распаковывай в `/`, используй `~/airflow-runtime` (Шаг 2).
- **`airflow version` падает после relocate** — пришли вывод; чаще всего не хватает
  `LD_LIBRARY_PATH` к `~/airflow-runtime/opt/python3.10/lib` (скрипт его выставляет сам).
- **`DPI-1047` / Oracle не находит клиент** — всплывает только при запуске задачи к
  Oracle, не при парсинге; разбираем на Шаге 5.
- **`Не задана переменная окружения ETL_ORACLE_MAIN_HOST`**, хотя она в `.env` —
  `.env` не был загружен при запуске standalone. Запускай через `local/airflow-local.sh`
  (он читает `.env`) либо инлайн с `set -a; . .env; set +a`. После правок `.env`
  standalone нужно **перезапустить**.
- **Postgres `could not initiate GSSAPI ... not found in Kerberos database`** — на dev-PC
  из-за доменного Kerberos. Добавь в `.env` строку `PGGSSENCMODE=disable` (libpq читает
  её для всех подключений, включая metadata-БД airflow). Для разовой команды передай
  `gssencmode='disable'` в `psycopg2.connect(...)`.
- **Postgres `база данных "<логин>" не существует`** — не указан `dbname`; libpq берёт
  имя БД = имя пользователя. Укажи `dbname='postgres'` для подключения к существующей БД.
- **`DPI-1047 ... libaio.so.1: cannot open shared object file`** — Instant Client
  тянет системную libaio, которой нет на dev-PC. Скопируй её с сервера в каталог
  instantclient (он в `LD_LIBRARY_PATH`):
  `cp -L /usr/lib/x86_64-linux-gnu/libaio.so.1 …` на сервере →
  `scp … ~/airflow-runtime/opt/oracle/instantclient_19_3/` на dev-PC.
- **«scheduler does not appear to be running» при пулах/замках (аудит)** — это
  `SequentialExecutor`: одна задача за раз, выполняется внутри scheduler, поэтому
  долгая задача (`etl_lock`) морозит heartbeat, а параллельные линии стоят `queued`.
  Для параллелизма нужен `LocalExecutor` + Postgres (SQLite параллелизм не умеет):
  `ETL_LOCAL_EXECUTOR=LocalExecutor ETL_LOCAL_DB_CONN=postgresql+psycopg2://USER:PWD@HOST:5432/airflow_local bash local/airflow-local.sh`.
  Параллелизм на dev-PC стоит ограничить: `ETL_LOCAL_PARALLELISM=4` (по умолчанию уже 4).
- **`DPI-1047 ... Cannot locate a 64-bit Oracle Client`** (без libaio) — не найден сам
  Instant Client; задай `ETL_ORACLE_LIB_DIR=~/airflow-runtime/opt/oracle/instantclient_19_3`
  в `.env`.
- **`FileNotFoundError: ... 'airflow'` при `standalone`** — `airflow` не в PATH или
  шебанги не починены. `airflow-local.sh` добавляет venv в PATH сам, а шебанги чинит
  `relocate-venv.sh` (Шаг 3). Если чинишь шебанги вручную в интерактивном bash —
  сначала `set +H` (иначе `!` в `#!` раскроется как история команд).
- **`port 8080 in use`** — `ETL_LOCAL_PORT=8081 bash local/airflow-local.sh`.
- **Мало памяти** — закрой лишнее; `airflow standalone` в лёгком режиме ест ~0.7–1 ГБ.
- **Распаковал не в `~/airflow-runtime`** — укажи свой путь:
  `ETL_LOCAL_RUNTIME=/твой/путь bash local/airflow-local.sh`.

# Перенос правок с GitHub через флешку

Между рабочим ПК и интернетом только флешка, а с GitHub скачивается ровно одно —
`Code → Download ZIP`, архив всего дерева. Раскладывать его копированием папок с
заменой нельзя, и вот почему: **копирование добавляет и обновляет, но никогда не
удаляет и не переименовывает.** В tools/ так накопились пятнадцать старых сборок
фронтенда и файлы под прежними именами (`SqlArea.jsx` рядом с пришедшим ему на
смену `CodeArea.jsx`). Это грязь, но безобидная.

Опасно то же самое в `etlFolder/`: **удалённая линия не удалится**. Её фрагмент
останется лежать в `config.d/`, и даг подхватит его как ни в чём не бывало —
молча, потому что для него это просто ещё одна запись конфига.

## Как переносить

**Запускать из папки проекта** — репозиторий скрипт ищет от текущего каталога,
а не от того места, куда его положили.

Windows (PowerShell), команда `python`, а не `python3`:

```powershell
cd C:\путь\к\Etl
python tools\sync_zip.py D:\Etl-main.zip --base      # ПЕРВЫЙ раз
python tools\sync_zip.py D:\Etl-main.zip             # дальше всегда так
python tools\sync_zip.py D:\Etl-main.zip --dry-run   # только посмотреть
```

Linux:

```bash
cd ~/Etl
python3 tools/sync_zip.py /media/flash/Etl-main.zip --base
python3 tools/sync_zip.py /media/flash/Etl-main.zip
python3 tools/sync_zip.py /media/flash/Etl-main.zip --dry-run
```

**Где запускать.** На том ПК, где лежит ваш клон — тот самый, из которого идёт
`dev-push.sh` в gitea. Архив достаточно принести туда на флешке.

**Распаковывать архив не нужно** — скрипт делает это сам, во временную папку.
И главное: распакованная папка `Etl-main` **не является рабочей копией**. Файлы
в ней есть, а истории (`.git`) нет, значит сливать нечего — запуск оттуда ничего
не даст. Если запустить не там, скрипт поищет копию рядом и назовёт найденное.

**Про команду.** Нужен **python3**: на рабочей машине `python` — это второй
питон, и он падал с `SyntaxError` на первой же строке. Теперь скрипт это
переживает — он написан так, что разбирается и вторым питоном, и при запуске
под ним сам перезапускается третьим. Так что работают обе команды, но
`python3` честнее.

**Путь к архиву можно не набирать.** Достаточно имени файла:

```bash
python3 tools/sync_zip.py Etl-main.zip --base
```

Скрипт поищет его на подключённых носителях (`/media`, `/run/media`, `/mnt`,
`/run/user/*/media`, на Windows — корни дисков) и напечатает, какой именно взял.
Нашлось несколько одноимённых — покажет список и попросит указать полный путь:
развернуть не тот архив дороже, чем один раз его набрать.

Так сделано потому, что **точка монтирования не постоянна**. Тот же носитель
после переподключения назывался уже иначе:

    …by-id-usb-JetFlash_Transcend_4GB_9T7MN722
    …by-id-usb-JetFlash_Transcend_4GB_9T7MN722-0:0-part1

Полный путь, разумеется, тоже работает. А `/dev/sdc1` — нет: это устройство, а
не каталог, файлов по такому пути не бывает (скрипт про это скажет отдельно).

Нужен `git` в PATH (на Windows — Git for Windows) и python 3.7+. Если запустить
не из той папки или ошибиться в имени архива, скрипт скажет об этом текстом и
покажет, какие `*.zip` рядом лежат, — трассировок не будет.

Архив — это снимок дерева, а git умеет сливать снимки. Скрипт заводит ветку
`github-snapshot`, каждый принесённый архив кладёт на неё коммитом, и дальше идёт
обычное трёхстороннее слияние:

| | что это |
|---|---|
| база | **прошлый** принесённый архив |
| их | нынешний архив |
| наше | ваша ветка со всеми вашими правками |

Отсюда всё нужное получается само:

* файл был в прошлом архиве, а в новом его нет → **удаляется** (то, чего
  копирование не делало никогда);
* файла нет ни в одном архиве → он **ваш**, его не трогают вовсе. Ваши запросы в
  `customQueries/`, ваши структуры, ваши линии — целы;
* файл поменялся и у вас, и в архиве → **конфликт**, git пометит его в тексте, и
  вы решаете сами. Ровно то предупреждение, которое нужно: «посмотри глазами, тут
  моё разошлось с твоим»;
* всё, что тронуто в `etlFolder/` и `dags/`, отчёт перечисляет **поимённо и
  всегда** — даже когда слияние прошло без конфликта. «Слилось молча» в ваших
  областях не означает «этого хотели».

Заодно исчезает вопрос «а перенёс ли я тот коммит, где менялся `etlFolder`».
Сливаются не коммиты, а снимки: сколько бы коммитов ни было между двумя архивами
и в каком бы порядке они ни шли, база — это всегда «прошлый архив».

## Ветка-снимок в историю не попадает

Слияния **веток** здесь нет. База известна и без общей истории — это прошлый
архив, — поэтому трёхстороннее слияние делается явно (`read-tree -m база наше
их`), а результат ложится **обычным коммитом** с одним родителем.

Так пришлось сделать после того, как первая версия «пришивала» снимок к ветке
слиянием `-s ours`. Дерево при этом не менялось, и выглядело безобидно — ровно
до `dev-push.sh`, который синхронизируется с сервером **перемещением**
(`git rebase origin/test`). Перемещение берёт все коммиты, каких нет на сервере,
и там оказывается коммит-снимок: **сирота с полным деревом GitHub**. Наложить
его на серверную ветку — это `add/add` по каждому файлу репозитория. На рабочей
машине вышло шесть десятков конфликтов на ровном месте.

Поэтому `--base` теперь не трогает ни дерево, ни историю: просто заводит
локальную ветку-снимок, чтобы следующему архиву было с чем сравниваться.

**Осталась старая база?** Скрипт это заметит и откажется работать, показав
команду очистки: `git rebase --onto origin/test <коммит> HEAD`. Ваши
собственные коммиты при этом сохранятся.

## База двигается только после успеха

Отказ на грязном дереве, «нет» на вопрос, Ctrl-C, конфликт — не считаются
переносом. Иначе повтор той же команды не принёс бы уже ничего, и правки
пропали бы молча между двумя архивами.

Конфликт отмечается файлом `.git/etl-sync-pending`. При следующем запуске по
нему видно, чем кончился разбор: `HEAD` сдвинулся — конфликты закоммичены,
архив засчитан применённым; `HEAD` на месте — откатились, и тот архив придёт
снова.

**База ушла вперёд, а правки не пришли?** Признак — отчёт показывает `0/0/0`
на архиве, в котором точно что-то менялось: база уже равна этому архиву, хотя
дерево его содержимого не получало. Так вела себя первая версия — двигала базу
до слияния. Вернуть базу на прошлый архив:

```bash
git reflog show github-snapshot          # ветка помнит все свои значения
git update-ref refs/heads/github-snapshot <строка до неудачного переноса>
python3 tools/sync_zip.py <архив> --dry-run   # в отчёте должны появиться правки
```

Сверять есть с чем: скрипт печатает `Прошлый архив: <коммит>` при каждом запуске.

Мусор, накопленный прошлыми копированиями, первое слияние не тронет: этих файлов
нет ни в одном снимке, значит для git они ваши. Отчёт назовёт их поимённо —
снести один раз руками (`git rm`), дальше всё делает слияние.

Исключение — `tools/webui/dist/assets/`. Там ваших файлов не бывает вовсе, всё
порождает сборка, и имя каждого файла содержит хэш: правка не заменяет файл, а
кладёт рядом ещё один. Копирование с заменой накопило там 22 файла при двух
нужных, и понять глазами, какой из них живой, нельзя. Поэтому в этом каталоге
правило перевёрнуто: чего нет в принесённом снимке — то мусор, и слияние его
убирает, называя поимённо. Если снимок про каталог ничего не знает (архив собран
без сборки), не трогается ничего.

## Мелкие правки

Если пришло две строки — переносить архивом незачем, правьте руками как раньше.
Скрипт нужен там, где менялось многое, и особенно там, где что-то **удалялось**
или переименовывалось.
