# Локальный airflow на dev-PC (Фаза 1)

Лёгкий airflow прямо на рабочем ПК для экспериментов: правишь даги/код в VS Code —
airflow видит изменения сразу, без копирования. Запуск одной командой, остановка
по Ctrl-C, все файлы видны в обычном проводнике.

- **Без Docker.** Берём готовый venv с сервера → точный паритет с продом (airflow
  2.7.2, Python 3.10, cx_Oracle 8.3.0, psycopg2 2.9.9), и никакой возни с контейнерами.
- **Лёгкий режим:** SQLite + SequentialExecutor, без Postgres/Redis.
- **Изоляция:** на прод/тест-сервер это не влияет никак.

Предпосылки: dev-PC и сервер — Astra 1.7 x86-64 (совпадают), на dev-PC есть `sudo`,
свободно ~2 ГБ на диске, dev-PC достаёт боевые БД по сети.

---

## Шаг 1. Упаковать runtime на сервере

```bash
ssh devel@airflow
sudo -s
# скопируй на сервер local/pack-runtime.sh (или просто выполни команды из него):
bash pack-runtime.sh
```

Получится `~/airflow-runtime-ГГГГММДД.tar.gz` (~1 ГБ) в домашней папке `devel`.

## Шаг 2. Перенести и распаковать на dev-PC

```bash
scp devel@airflow:/home/devel/airflow-runtime-*.tar.gz ~/
sudo tar xzf ~/airflow-runtime-*.tar.gz -C /
```

Появятся `/opt/python3.10`, `/opt/airflow/venv`, `/opt/oracle` — по тем же путям,
что на сервере (это важно: venv остаётся рабочим без правок).

Быстрая проверка, что интерпретатор и airflow живые:
```bash
/opt/airflow/venv/bin/airflow version      # ожидаем 2.7.2
/opt/airflow/venv/bin/python --version     # ожидаем 3.10.7
```

## Шаг 3. Запустить локальный airflow

Из корня репозитория:
```bash
bash local/airflow-local.sh
```

При первом запуске airflow сам создаст БД и напечатает логин/пароль для UI.
Открой <http://localhost:8080>. Остановка — Ctrl-C.

Что делает скрипт:
- `AIRFLOW_HOME = ~/airflow-local` (рантайм airflow, **вне** репозитория);
- даги берутся из `dags/` этого репозитория, код — из `Functions/`, `Src/`, `Connect/`
  (через `PYTHONPATH`);
- `ETL_MODE=""`, `ETL_FULL_PATH=<корень репо>/` → конфиг читается из `etlFolder/`
  (dev-версия, не Prod).

На этом шаге проверяем главное: **venv с сервера завёлся и DAG-и парсятся** — в UI
не должно быть красных ошибок импорта. Для парсинга и UI пароли к БД не нужны
(подключения происходят только при запуске задачи).

## Шаг 4 (опционально). Реальные запуски задач против БД

Чтобы запускать задачи (а не только смотреть, как даги парсятся), нужны реквизиты БД.
Скопируй шаблон и впиши реальные значения — файл `.env` в `.gitignore`, в репозиторий
не уйдёт:
```bash
cp .env.example .env
# отредактируй .env: ETL_ORACLE_*, ETL_POST_*
```
`airflow-local.sh` подхватит `.env` автоматически.

> Примечание: сейчас `Connect/__init__.py` берёт реквизиты из захардкоженных заглушек,
> а не из переменных окружения (ветки с `os.environ` закомментированы). Чтобы `.env`
> реально заработал для подключений, эти ветки нужно раскомментировать — это отдельный
> небольшой шаг, делаем после того, как убедимся, что airflow поднимается.

## Если что-то не так

- **`airflow: команда не найдена` / скрипт ругается на venv** — не выполнен Шаг 2
  (нет `/opt/airflow/venv`).
- **`DPI-1047` / Oracle не находит клиент** — проверь, что распаковался
  `/opt/oracle/instantclient_19_3`; скрипт сам добавляет его в `LD_LIBRARY_PATH`.
  Это всплывает только при запуске задачи к Oracle, не при парсинге.
- **`port 8080 in use`** — запусти на другом порту: `ETL_LOCAL_PORT=8081 bash local/airflow-local.sh`.
- **Мало памяти** — закрой лишнее; `airflow standalone` в лёгком режиме ест ~0.7–1 ГБ.
- **Венв не в `/opt/airflow/venv`** — укажи путь: `ETL_LOCAL_VENV=/путь/к/venv bash local/airflow-local.sh`.
