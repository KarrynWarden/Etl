# ETL: универсальный синхронизатор Oracle ↔ PostgreSQL

Один универсальный процесс `Functions.do_etl.Do_etl` поверх стратегии
`etl_log_iud_row` для всех 4 направлений: Orcl→Post, Post→Orcl, Post→Post,
Orcl→Orcl. Корректность переноса проверяет такой же универсальный аудит
`Functions.do_audit.Do_audit` (один на все таблицы и направления).

## Структура

```
Functions/
    do_etl.py                  — ядро переноса
    do_audit.py                — ядро аудита (тот же config.json)

    functionsFile/

etlFolder/

    queries/
```

## Аудит

`Functions.do_audit.Do_audit` — единая, универсальная проверка корректности
переноса; параметры берёт из того же `config.json`, что и ETL (ключ
`tableNameEtlJobs+dbMaster+dbSlave`). Никаких `doctype`/`iperson`/`medree` в
коде: всё, что отличается между таблицами, лежит в конфиге.

Логика: из `etl_jobs` берутся группы линии с `isokaudit != 1` (и `!= 4` —
это зона ETL), за каждый период сравниваются множества записей ведущей и
ведомой (с приведением Oracle NUMBER/DATE → Postgres decimal/date), и в
`etl_jobs.isokaudit` пишется результат:

| isokaudit | смысл |
|-----------|-------|
| `1`  | данные идентичны |
| `-4` | есть отличия / дубликаты |
| `-2` | ошибка при проверке группы |

Ключевые решения:

- **Без разбиения по направлениям.** Одно ядро на все 4 направления; один
  DAG `AuditAllTest` итерирует все линии из `config.json`
  (`iterAuditLines`) — отдельных файлов под `orcl→pg` / `pg→orcl` нет.
- **doctype** — никаких `handle_doctype()`: срез задаётся теми же
  `filterClause` / `filterClauseSlave`, что и при переносе.
- **iperson: сравнивать не все поля.** Переносятся все колонки, а аудит
  сравнивает все *кроме* перечисленных в `auditExcludeFields` (для iperson —
  join-поля `doctype, docser, docnum, docdate, name_vp` из `idoc`/`spdocper`).
  Задаётся в `config.json` строкой колонок через запятую
  (`"doctype, docser, ..."`); список тоже принимается (легаси).
- **Чекпоинт по группам.** Статус коммитится сразу после каждой группы.
  Долгий iperson (~1000 групп, иногда по ~500k строк) при SIGTERM на 5-м
  часу теряет только текущую группу; оставшиеся (`isokaudit != 1`) добирает
  следующий запуск. `AuditAllTest` запускается ежечасно 18–23ч —
  это заменяет старый костыль с двумя запусками в 17/18ч.

- **Расхождения не уводят в авто-ретрай.** Если найдены `-4`/`-2`, запуск
  красится 🟥, но БЕЗ ретраев и БЕЗ заморозки (`AirflowFailException` +
  `error_class='record'`). Ретрай аудита почти не помогает (реальная
  ошибка переноса повторится), а 6 ретраев по несколько часов зря грузят
  железо. Статусы уже в `etl_jobs.isokaudit` — человек смотрит и решает,
  перезапускать аудит/перенос вручную или нет.

- **`skipAudit`** в `config.json` — линия временно не проверяется (таблица
  «на ремонте» / даг ещё не готов): `iterAuditLines` вообще не создаёт для
  неё аудит-задачу. Не забыть снять пометку, когда линия будет готова.

- **ETL стоит, аудит параллелен.** На время прогона задача-замок `etl_lock`
  занимает весь пул ETL (`ETL_POOL_SLOTS` = размеру пула `Test`), поэтому
  ETL-переносы (`pool_slots=1`) не стартуют и аудит не пометит недоношенный
  перенос как успешный. Сами аудит-линии живут в `default_pool` и потому
  выполняются **параллельно** друг другу (а не сериализуются, как было бы
  при занятии всего пула каждой линией). Линия не трогает БД, пока не получит
  XCom-сигнал «замок взят» — это убирает стартовую гонку. `freeze_watcher`
  тоже в `default_pool`, поэтому замороженные ETL-даги слоты ETL-пула не
  держат и взять замок не мешают.

## Режимы обработки

1. **`iud`** (по умолчанию) — точечные апдейты. Триггеры на ведущей пишут в
   `etl_log_iud_row` (`oper IN ('IU','D')`, `isetl = 0`). Процесс читает
   необработанные записи, точечно переносит в ведомую через UPSERT/MERGE и
   выставляет `isetl = 1`. Решает проблему отложенного коммита. Доп.
   запускает массовое обновление групп с `isokaudit = 4`.

2. **`section_compare`** — срезовый режим для medree:
   - сравниваются срезы `(period, lastupdate, количество записей)` на ведущей и
     ведомой: группа обновляется, если разошлись множества `lastupdate` **либо**
     счётчики. Одного `lastupdate` мало — удаление строки, не державшей
     максимум, множества не меняет, а данные уже другие;
   - дополнительно подтягиваются группы с `isokaudit = 4` в `etl_jobs`;
   - для каждой группы — полное `DELETE WHERE period = X [AND filter]`
     и перезаливка из ведущей;
   - журнал `etl_log_iud_row` **не читается вовсе**, поэтому триггер на
     ведущей этому режиму не нужен.

2a. **`section_compare_with_iud`** — то же самое ПЛЮС журнал:
   - к группам добавляются те, по которым в `etl_log_iud_row` есть `isetl = 0`;
   - после успешной обработки помечаются `isetl = 1` те записи журнала,
     которые существовали в момент старта (новые остаются для
     следующего запуска — снимает гонки);
   - **требует триггера** на ведущей.

   Раньше это был один режим `section_compare`: журнал опрашивали у всех, хотя
   пишут в него единицы, и линии вроде `medree_cons` (у которых и первичного
   ключа-то нет) получали замечание о ненужном им триггере. Теперь режим
   выбирается явно: нет триггера — `section_compare`, есть и нужна быстрая
   реакция — `section_compare_with_iud`.

3. **`section`** — упрощённая срезовая логика: обрабатываются только
   группы с `isokaudit = 4`, каждая перезаливается целиком (DELETE группы в
   ведомой + заливка из ведущей). Групп нет — прогон завершается пропуском
   (⬜). Используется, когда список пересчитанных периодов знает не ETL, а
   тот, кто их пересчитал: ручной триггер массового переобновления либо
   джоб **внутри** ведущей БД, который сам ставит `isokaudit = 4`
   (`Medree_prdisp`, см. «Medree_prdisp: процесс из двух частей»).

4. **`delete_insert`** — событийный (как `iud`, читает `etl_log_iud_row`
   по `idrw`), но для случая «один `idrw` = несколько строк ведомой»
   (podcheck: одна запись-источник даёт строки разных `doctype`,
   и при смене атрибута строка между этими `doctype` переезжает). На каждое
   событие `idrw` делается **одно и то же, независимо от типа операции**:
   `DELETE` всех строк этого `idrw` в ведомой + `INSERT` того, что **сейчас**
   отдаёт по нему ведущая (если ничего — не вставляем). Это ловит
   «осиротевшие» строки при смене `doctype` (старый `doctype=2 idrw=123`
   остаётся, когда запись переехала в `doctype=3`), чего `upsert` в `iud` не
   делает. Дёшево — только изменённые `idrw`, без полного скана.

   **`conflictExtra` / `conflictWhere` в этом режиме не нужны** — строки
   `idrw` уже удалены, конфликтовать не с чем, поэтому заливка идёт простым
   `INSERT` без `ON CONFLICT` (см. `_buildUpsertSql`: ключи просто
   игнорируются). Уникальный индекс под `ON CONFLICT` на ведомой тоже не
   требуется. А вот `filterClauseSlave` нужен по-прежнему: он ограничивает
   `DELETE` своим срезом, иначе линия снесла бы чужие `doctype`.

   **Несколько ведущих таблиц на одну линию** — нормальный случай: `doctype=6`
   собирается из `PODCHECK` и `SPPODNORM`, у которых независимая нумерация
   ключей. Триггеры ставятся на обе и пишут ОДИН `tablename`; совпадение
   `idrw` из разных источников не ломает перенос — удаляются и заливаются
   заново все строки этого `idrw` в пределах среза.

   **Почему `oper` (IU/D) не используется.** Раньше ветки IU и D были разными:
   на `D` строки только удалялись. Если у одного `idrw` в ведущей было
   несколько строк и удалили одну из них, событие `D` сносило в ведомой **все**
   строки этого `idrw` и не возвращало те, что в ведущей ещё живы — данные
   терялись. Теперь источник истины — текущее состояние ведущей, а не тип
   события в журнале.

   **`period` декуплён от логики.** Триггер «глупый»: пишет `tablename`,
   `idrw`, `oper`, `period` = удобное-для-человека значение (для expmed —
   `docexpdt`, неверное для `doctype=4`). В логике `period` из
   `etl_log_iud_row` НЕ используется — реальные затронутые группы `etl_jobs`
   берутся из данных: для удаляемых строк из **ведомой** (до удаления,
   `SlavePeriodsById*.sql`), для вставляемых из **ведущей** (колонка
   `periodColumn` в строке). Объединение помечается `isokaudit=0` для
   перепроверки аудитом.

   **`EXPMED` из этого режима переведён в `section_compare_with_iud`.**
   `delete_insert` ходит только по журналу и только по конкретному `idrw`:
   расхождение, возникшее мимо триггера (или до того, как журнал доехал),
   линия не видит вовсе — сравнивать ей нечего. Срезовый режим сверяет
   `(период, lastupdate, количество)` на обеих сторонах и перезаливает
   разошедшуюся группу целиком, а журнал остаётся как ускоритель реакции.
   Переезд строки между `doctype 2↔3↔4` он переживает так же: `filterClause` /
   `filterClauseSlave` = `doctype IN (2,3,4)` держат срез, и группа
   перезаливается вся, а не построчно. У линии стоит `truncatePeriod`: у
   ведущей `createdate` — oracle `DATE` (`docexpdt`/`docpenaltydt`, драйвер
   отдаёт `datetime`), у ведомой — postgres `date`; без приведения к дню
   группы не совпали бы никогда и таблица перезаливалась бы на каждом прогоне.
   Цена режима — скан источника каждый прогон (`PODCHECK` пока остаётся на
   `delete_insert`).

5. **`query_section`** — список групп для перезаливки даёт **пользовательский
   запрос** `periodsSql` (а не журнал и не сравнение срезов). Всё остальное — как
   в других режимах: группа регистрируется в `etl_jobs`, перезаливается целиком
   тем же `_processGroupUpdate` (DELETE группы + заливка), пишется `etl_log`.
   Колонки `periodsSql` должны соответствовать периоду ведущей: одна колонка-дата
   либо `year[, month[, day]]`. Применяется, когда пересчитанные периоды знает
   ваш SQL, а триггера на ведущей нет и пометить `isokaudit = 4` некому. Если
   пометить может сам пересчитывающий джоб — берите `section`: он проще и не
   требует держать логику окна в двух местах (так сделан `Medree_prdisp`).

## Период группы (любой режим)

Период — **свойство таблицы, а не режима**. `periodColumn` / `slavePeriodColumn`
принимают две формы, независимо для ведущей и ведомой (у одной может быть
составной, у другой цельный):

| Форма | Значение |
|-------|----------|
| `"createdate"` | одна колонка-дата (как было раньше) |
| `{"year": "god"}` | только год → `ГГГГ-01-01` |
| `{"year": "year", "month": "month"}` | год+месяц → `ГГГГ-ММ-01` |
| `{"year": "y", "month": "m", "day": "d"}` | год+месяц+день |

На границе с SQL составной период сравнивается **по частям**
(`year = :y AND month = :m`) — это sargable и использует индексы, а собирается в
дату только там, где нужна дата (JOIN с `etl_jobs`, запись периода). Имена
колонок — как в своей БД (Oracle ВЕРХНИЙ, Postgres нижний); в конструкторе есть
блок «Период группы» с переключателем «одна колонка / составная» для каждой
стороны.

### Гранулярность группы: `truncatePeriod`

Для одной колонки-даты флаг `truncatePeriod` решает **сразу два вопроса, и
одинаково** — как сравнивается период в SQL и что считается одной группой в
Python (`_periodKey`):

| `truncatePeriod` | Группа | Когда |
|------------------|--------|-------|
| `true` | **день** (`TRUNC`/`DATE`, ключ — `datetime.date`) | стороны хранят период по-разному или время в нём незначимо. `iprkdept`: ведущая Oracle `DATE` (драйвер отдаёт `datetime`), ведомая Postgres `date` (отдаёт `date`) |
| `false` (умолч.) | **точное значение, вместе со временем** (ключ — `datetime`) | время значимо и есть с обеих сторон. `medree`: у `dcalc` есть время, отдельным пересчётом считается каждое конкретное значение |

Тип приводится к общему в обоих случаях (`date` → `datetime` в полночь), поэтому
Oracle `DATE` и Postgres `timestamp` сравниваются корректно. Это важно, потому
что в `section_compare[_with_iud]` группы приходят из двух-трёх источников —
сравнение срезов master/slave, `isokaudit = 4` в `etl_jobs` и (только в
`_with_iud`) журнал `etl_log_iud_row` — и ключ у всех обязан быть одинаковым: иначе одна и та же группа попадает в набор
дважды в разном виде, а `sorted()` по смеси `date` и `datetime` падает с
`TypeError`. Тем же ключом группу берёт аудит (`do_audit`): при
`truncatePeriod = false` безусловное приведение к дате давало полночь, которой в
данных нет, обе выборки возвращали 0 строк — и группа помечалась «идентична»
(ложный зелёный).

Отдельный флаг `truncateLastupdate` — про то же, но для `lastupdate`: сравнивать
его по дате, а не по timestamp.

| Длина / scale столбца | в проверке игнорируются |
| Подмножество ETL-полей | `etlFields` |

| Аудит группы (`isokaudit=4`) | один и тот же путь обработки |

## NULL-период — обычная группа

Период группы может быть **пустым**, и это не ошибка данных: у `expmed` поле,
которое служит периодом, какое-то время `NULL`, а строки при этом надо возить,
сверять и учитывать. Поэтому `NULL` — полноправный ключ группы во **всех**
режимах, а не только в срезовых.

Как это сделано. Сравнить `NULL` через `=` нельзя, поэтому в SQL обе стороны
приводятся к сентинелу: `COALESCE(period, TO_DATE('1900-01-01','YYYY-MM-DD'))`.
Значение и его python-двойник лежат в одном месте — `Src/generalQueries.py`
(`PERIOD_SENTINEL_SQL`, `PERIOD_SENTINEL`, `periodBind`), оттуда их берут и
перенос, и аудит, и запись в `etl_log`.

**В бинд `NULL` не уходит никогда** — подстановку делает Python
(`_periodBinds` / `periodBind`). Иначе пришлось бы гадать, каким типом драйвер
пошлёт `None`: cx_Oracle по умолчанию отправляет его строкой, а
`COALESCE(строка, дата)` — это ORA-00932. Единственное место, где `NULL`
доезжает до БД как есть, — `INSERT` новой группы в `etl_jobs`, и там стоит
явный `CAST(:period AS DATE)`.

Для составного периода (`{"year": ..., "month": ...}`) сентинел числовой (`-1`),
а пустой год означает ту же `NULL`-группу.

Сортировка периодов идёт через `_periodSortKey` (`NULL` последним): обычный
`sorted()` на смеси `date` и `None` падает с `TypeError`.

> **Требование к схеме:** `etl_jobs.period` должен допускать `NULL`. Если на
> колонке стоит `NOT NULL`, регистрация такой группы упадёт на `INSERT` —
> ограничение снимает администратор БД. Проверить:
> `SELECT nullable FROM all_tab_columns WHERE table_name='ETL_JOBS' AND column_name='PERIOD'`
> (Oracle) / `SELECT is_nullable FROM information_schema.columns WHERE
> table_name='etl_jobs' AND column_name='period'` (Postgres).

## Фильтры сторон: `filterClause` / `filterClauseSlave` / `filterClauseMaster`

Три ключа, и они **независимы** — ставить парой не обязательно, любой можно
задать в одиночку.

| Ключ | Куда попадает | Перенос | Аудит |
|------|---------------|---------|-------|
| `filterClause` | обёртка вокруг источника: `SELECT * FROM (<selectSql>) src WHERE …` | да | да |
| `filterClauseSlave` | `DELETE` по id, `DELETE` периода, `SlavePeriodsById`, выборка ведомой в срез-сравнении | да | да |
| `filterClauseMaster` | условие в `RecordSelectById` / `RecordSelectGroup` | да | **нет** |

Отсюда два практических следствия. Первое: фильтр ведущей задавайте
`filterClause` — `filterClauseMaster` в аудите не применяется
(`do_audit._buildMasterSql`), и перенос с аудитом разъедутся. Второе:
**`filterClauseSlave` в запись (`INSERT … ON CONFLICT` / `MERGE`) не входит
ни на одной СУБД** — запись идёт строго по первичному ключу. На Oracle он
раньше приклеивался к `ON` у `MERGE`, и это давало ORA-38104, если фильтр
стоит по переносимой колонке (Oracle запрещает обновлять колонки из `ON`),
а строку, не подошедшую под фильтр, отправляло в `NOT MATCHED` → `INSERT`
→ дубль по PK. Смысл ключа — «какие строки ведомой относятся к линии» при
сравнении и удалении, а не ограничение записи: совпал PK — это та же
логическая строка.

Симметрия нужна не всегда. У mocheck фильтры парные, потому что срез по
`doctype` существует с обеих сторон. А у `eindexmoPostOrcl` фильтр стоит
**только на ведомой** (`YEAR >= 2019`): разовой заливкой Oracle→Postgres
взяли только 2019+, на Oracle остались доисторические строки, которых на
ведущей нет и не будет, и без фильтра аудит сравнивал их с пустотой.

Односторонний фильтр держится на инварианте: **сторона, которую фильтр не
режет, не должна порождать строки, которые фильтр на другой стороне
прячет.** Иначе строка честно переедет, а в аудите одна сторона её покажет,
другая спрячет — и период останется `-4` навсегда.

И общее для всех трёх: сужение фильтра **не** порождает `DELETE` на ведомой.
Строка, выпавшая из выборки ведущей, остаётся на ведомой сиротой; если
фильтр ведомой её прячет, аудит об этом не скажет.

## Справочники и разовый перенос

Кроме «сложного» ETL (точечные апдейты по журналу, свой даг на таблицу) есть две
упрощённые схемы — **полная перезаливка** ведомой (`DELETE FROM ведомой` + пакетный
`INSERT` всех строк ведущей). Обе описываются короткими фрагментами и гоняются
общими дагами (отдельный даг на таблицу не нужен):

| Тип | Фрагменты | Даг | Расписание | Логика переноса |
|-----|-----------|-----|------------|-----------------|
| **Справочник** (regular) | `etlFolder/SpTableName.d/*.json` | `SpEtlNew` (`dags/SpDagNew.py`) | по интервалу | `Functions.spEtlNew.SpEtl` |
| **Разовый перенос** (once) | `etlFolder/SpOnce.d/*.json` | `SpEtlOnce` (`dags/SpOnce.py`) | ручной триггер | тот же `SpEtl` |

Ключ фрагмента = `<МЕТКА_ВЕДУЩЕЙ><DbMaster><DbSlave>` (напр. `SPMKBOrclPost`,
`ipersonactOrclPost`) — направление кодируется суффиксом из `Post`/`Orcl`. Тело:
`tableNameSlave`, `addSql` (INSERT в ведомую), `selectSql` (SELECT из ведущей),
опц. `dependence` (у справочника), `disabled`, `_doc`. Плейсхолдеры INSERT — под
диалект ведомой: Oracle `VALUES (:1, :2, …)` (`cursor.executemany`), Postgres
`VALUES %s` (`psycopg2.extras.execute_values`).

- **Что запускает перенос справочника: его собственный триггер.** `SpEtlNew` не
  сравнивает данные и не читает журнал — он раз в 5 минут берёт
  `SELECT DISTINCT tablename FROM etl_jobs WHERE isokaudit = 0` и гоняет все
  линии, у которых `dependence` равна этой метке (после успеха ставит
  `isokaudit = 1`). Ноль туда пишет **триггер на ведущей**:

  ```sql
  -- Oracle
  UPDATE koknaev.etl_jobs SET isokaudit = 0, last_success_ts = sysdate
   WHERE tablename = 'CALENDAR';
  -- Postgres: общая функция public.tr_etl_table_iud_func(), метка приходит
  -- аргументом триггера: EXECUTE PROCEDURE tr_etl_table_iud_func('EINDEXSTRU')
  ```

  Готовые шаблоны — `oracleSetup/09_sp_audit_triggers.sql` и
  `postgresSetup/03_sp_audit_triggers.sql`; собрать и поставить из конструктора —
  блок «Триггер справочника» (собрать DDL; ставит его в БД администратор).
  Без триггера справочник не перенесётся
  никогда, при этом **ни одна задача не покраснеет**: дагу просто нечего делать.
  Столь же тихо ломается отсутствующая строка в `etl_jobs` — `UPDATE` по ней не
  изменит ничего. И то, и другое проверяет вкладка «Триггеры».

  `dependence` = явное поле фрагмента, иначе метка ведущей без цифры `1`/`2` на
  конце (`SPEINDEX1` → `SPEINDEX`) — так две линии одной таблицы делят одну
  зависимость и обновляются вместе.

- **Отключение таблицы (не удаление).** Флаг `"disabled": true` во фрагменте —
  регулярный даг `SpEtlNew` таблицу **пропускает**, но конфиг и SQL остаются на
  месте. Снятие флага возвращает таблицу в перенос. Удобно, когда таблица «на
  ремонте». Через конструктор — вкладка «Справочники / разовый» → «🚦 Вкл/выкл».
  Отключённые линии не показываются в списке правки (править нечего, пока не
  включишь) и не проверяются на вкладке «Триггеры».

- **Разовый перенос — параллельно.** `dags/SpOnce.py` создаёт **по задаче на
  таблицу**, поэтому Airflow гоняет их одновременно (в пределах пула/parallelism),
  а не по очереди.

- **Два режима разового переноса.** `"append": true` во фрагменте `SpOnce.d/` —
  режим **дополнения**: ведомая НЕ очищается, строки из SELECT (обычно с WHERE)
  просто дописываются. Без флага — режим **переноса**: полная перезаливка
  (очистить + залить). Типичный сценарий: сперва перенос, затем тем же переносом
  дополнение с другим SELECT (ведомая и INSERT те же, меняется только запрос).

## Конструктор (веб-приложение / ноутбук)

`tools/dag_builder_ui.launch()` — интерфейс на ipywidgets с тремя вкладками:

- **Сложный ETL** — сборка/правка/архивирование линий do_etl (свой даг **или
  общий составной на несколько линий**, структуры, config.d); ядро —
  `tools/dag_builder.py`.
- **Триггеры** — проверка того, что есть **в БД**: на месте ли триггеры линий,
  журнал и служебные таблицы; ядро — `tools/trigger_builder.py`. См.
  «Триггеры: проверка и создание из конструктора».
- **Справочники / разовый** — сборка/правка справочников и разовых переносов,
  включение/отключение таблиц; ядро — `tools/sp_builder.py`. Два пути задания
  источника: **назвать ведущую** (SELECT/INSERT соберутся сами по сопоставленным
  колонкам) или **вставить свой SELECT** (колонки снимутся из курсора, сопоставишь
  со столбцами ведомой, получишь INSERT). Есть сопоставление колонок (без учёта
  регистра: Oracle отдаёт ИМЕНА в ВЕРХНЕМ, Postgres — в нижнем) и предпросмотр.
  В режиме правки текущее сопоставление и текущий INSERT восстанавливаются из
  сохранённого SQL — без обращения к БД.

Общее для обеих вкладок сборки:

- **Структуру снимает то, что реально будет источником.** Если заполнен «SQL
  ведущей» (свой SELECT) — колонки снимаются **по запросу** (описание курсора), и
  только если запроса нет — по таблице. Так же поступает рантайм: при заданном
  `selectSql` он сверяет структуру по описанию курсора этого запроса
  (`StructCheck*Query`), а не по таблице. Раньше структура всегда снималась с
  таблицы, поэтому колонка, которой в таблице нет (`null CHECKDIR` в SELECT), в
  структуру не попадала вообще — линия молча переносила её мимо. Первичный ключ из
  описания курсора не виден, поэтому он подмешивается из таблицы ведущей
  (`merge_table_pk`), а остальное правится руками.
- **Тип колонки можно указать вручную; колонки — добавлять и удалять.** В строке
  сопоставления имя и тип ведущей — обычные поля ввода, **🗑** убирает колонку из
  линии, кнопки под таблицей добавляют новую колонку ведущей или ведомой. Тип
  нужен там, где его неоткуда взять: у константы в запросе (`null CHECKDIR`,
  `2 CHECKDIR`) драйвер отдаёт «UNKNOWN» — такое поле подсвечивается как
  неизвестное. **Такие колонки рантайм сверяет только по имени** (см.
  `structCheck._isSubsetIgnoringUnknown`): тип, который проверяющий не может
  определить, не с чем сравнивать, поэтому вписанный вручную тип линию не ломает.
  Надёжнее всего задать тип прямо в запросе — `CAST(NULL AS NUMBER) CHECKDIR`.
  На вкладке справочников то же самое, но без типов: там json-структуры не пишутся,
  важен только состав и **порядок** колонок (вставка позиционная — при
  расхождении с числом колонок своего SELECT конструктор предупреждает).
- **«SQL периодов» видно только при `mode = query_section`.** Список групп из
  своего запроса читает ровно один режим; в остальных ключ `periodsSql` не
  пишется и файл не создаётся. Раньше поле висело в «Дополнительно» всегда — его
  заполняли впустую. И наоборот: `query_section` без этого запроса больше не
  собирается (понятная ошибка вместо линии, которой неоткуда взять группы).
- **«Создать и запушить»** — рядом с «Создать файлы» есть кнопка, которая после
  подтверждения (диалог-защита от мисклика) пишет файлы и делает
  `git commit` + `git push` текущей ветки. Требует настроенных git-реквизитов у
  пользователя, под которым крутится конструктор (на сервере — `jupyter`); если
  их нет, файлы всё равно создаются, а выложить можно обычным деплоем.

  **В коммит попадает не только текущая линия, а всё сохранённое** в
  `etlFolder/` и `dags/`. Это рассчитано на типовой сценарий: собрать несколько
  связанных линий кнопкой «Создать файлы», а последнюю выложить «Создать и
  запушить» — одним коммитом уедут все. Раньше индексировались только файлы
  текущей формы, поэтому предыдущие линии молча оставались несохранёнными в
  рабочей копии: их не видел ни `dev-pull` на ПК, ни хук деплоя (он обновляет
  Jupyter-клон только ff-only, а грязная копия это блокирует), и обнаруживались
  они уже как «несохранённые правки» с предложением их затереть. Что именно
  уедет — список показывается в диалоге подтверждения до нажатия «Да».
- **«Просто запушить»** — коммит + push уже сохранённых на диске изменений
  (`etlFolder/`, `dags/`), без генерации из текущей формы. Показывает список
  изменений перед выкладкой. Нужна, когда сохранил одно, потом наклацал в форме
  лишнее (форму не трогает), и чтобы выложить операции вкл/выкл, перевод и
  удаление (у них своего пуша нет).
- **Удаление линии насовсем** (с подтверждением и списком файлов). Для sp — во
  вкладке «Справочники / разовый» → «🚦 Вкл/выкл»; для сложного ETL — в панели
  «🗄 Архив». Убирает фрагмент, даг/SQL и структуры, если они не используются
  другими линиями (общие — не трогаются). В отличие от архива — насовсем.
- **Составной даг: несколько линий одним файлом.** Переключатель «Свой даг на
  линию / В составной даг» в форме сборки. Одна ведущая-запрос часто кормит
  сразу несколько линий (mocheck: `MEDCHECK`, `EXPMED`, `PODCHECK`,
  `TFOUTSCHET`, `TFINSCHET` из общего `MOCHECK.sql`) — отдельный даг на каждую
  означал бы N параллельных прогонов по одному источнику. Раньше сложить их в
  один даг можно было только руками; теперь конструктор пишет составной даг сам:

  ```python
  # dagbuilder: составной даг (список линий ниже правит конструктор)
  LINES = [
      ('MEDCHECK', 'Orcl', 'Post'),
      ('EXPMED',   'Orcl', 'Post'),
  ]
  ```

  Даг создаётся по задаче на линию (`makeEtlOperator`) + общий
  `addFreezeWatcher`, а `lineEnabled` в нём отсеивает архивные линии. Следующая
  линия **дописывается** в список: конструктор читает файл, добавляет кортеж и
  перезаписывает. Расписание, теги и режим ретраев у составного дага общие на
  все линии, поэтому у **существующего** дага они не меняются (иначе правка
  одной линии молча меняла бы поведение остальных).

  **Принадлежность линии даге записана в её конфиге** — ключ `groupDag`:

  ```json
  "EXPMEDOrclPost": { "...": "...", "groupDag": "MocheckOrclPost" }
  ```

  Раньше её искали обратным ходом — пробегали даги и смотрели, в чьём списке
  линия упомянута. Это работает только для дагов нашего формата, поэтому линия
  из дага, написанного руками, выглядела как линия **вообще без дага**: правка
  такой линии по умолчанию вставала на «свой даг на линию» и по «Создать
  файлы» заводила ей второй даг — тот же перенос начинал идти дважды. Обратный
  поиск остался как запасной для линий, заведённых до появления ключа.

  **Свободный текст в даге переживает перезапись.** Всё, что в docstring после
  строки-маркера `─── заметка …`, конструктор читает при разборе и кладёт
  обратно, когда перезаписывает файл. Так в машинном даге живёт объяснение
  «зачем он и что за линии» — то, ради чего такие даги раньше писали руками
  (в `MocheckOrclPost` это таблица doctype).

  `MocheckOrclPost` и `MedreeOrclPost` теперь **машинные** — конструктор их
  читает и переписывает. Ничего, кроме перечисления линий, они не делали, а
  состав задач после перевода тот же: сверен разбором старого и нового файла
  (task_id, все аргументы `makeEtlOperator`, аргументы `addFreezeWatcher` и
  параметры `DAG`) — совпадает дословно, так что история задач в Airflow не
  рвётся. `MedreeOrclPost` при этом получил `lineEnabled`, которого у него не
  было: раньше линию medree нельзя было убрать в архив вовсе (своего файла дага
  у неё нет, а флаг `disabled` даг игнорировал).

  Даг **со своей логикой** (а не просто перечислением линий) конструктор
  по-прежнему **не переписывает** — он виден в списке с пометкой «написан
  руками», и для него показывается готовая строка, которую нужно вписать
  самому. Сейчас таких дагов нет. Признак «наш» — комментарий-маркер
  `# dagbuilder: составной даг` в файле.

  **Переезд линии между дагами** (переключатель «свой даг ↔ составной») теперь
  доводится до конца: линия убирается из прежнего составного дага, а свой даг
  удаляется, если линия уехала в составной. Раньше конструктор только добавлял
  новое размещение, а старое оставалось — и линия работала из двух дагов сразу.
  Заодно свой даг нельзя назвать именем составного: такой файл был бы затёрт
  вместе со всеми перечисленными в нём линиями, и вместо этого будет ошибка.

- **Правка меняет только изменённое.** Сборка всегда выдаёт ПОЛНЫЙ комплект
  файлов линии (две структуры, фрагмент конфига, даг, свой SQL), но записывается
  из него лишь то, что реально отличается от лежащего на диске: поменял
  структуру ведомой — переписалась одна структура, поменял текст запроса — один
  `.sql`. Остальное отчёт показывает строкой «Не изменились». Сравнение не
  побайтовое: у json сверяется разобранное значение (структуры mocheck набиты
  руками табами, и переформатирование под `json.dumps` показывало бы 150 строк
  несуществующих изменений), у `.sql` — текст без крайних пробелов.

  Отдельной строкой отчёт называет **общие файлы**: `MOCHECK.sql` и структуры
  `structures/MOCHECK/*` — одни на пять линий mocheck, и правка запроса из формы
  `EXPMED` меняет запрос **всем** (это и требуется — линии различаются только
  фильтром по doctype, — но знать об этом надо до нажатия кнопки).
- **Архив линий без своего дага.** У линий mocheck- и medree-семейств
  (`PODCHECK`, `EXPMED`, `MEDREE_CONS`, …) нет отдельного файла дага — они
  перечислены внутри составного. Для них «в архив» = флаг
  `disabled` в конфиге (+`skipAudit`), а даг-итератор такие линии пропускает
  (`_dagHelpers.lineEnabled`). Удаление линии насовсем такой даг не сносит —
  из него убирается только строка этой линии.
- **Автозаполнение парного имени** (`⇄ имя по регистру БД`) — заполни имя одной
  таблицы, второе подставится с регистром своей БД (Oracle — ВЕРХНИЙ, Postgres —
  нижний). Схема при необходимости дописывается вручную (`to_db_case`).
- **Перевод разовый ↔ регулярный без пересборки** (вкладка «Справочники /
  разовый» → «🚦 Вкл/выкл») — фрагмент линии переезжает между `SpOnce.d/` и
  `SpTableName.d/`, а SQL остаётся на месте. Частый случай: справочник держали в
  разовом ради данных для разработки, а потом переводят на регулярный режим.

Веб-версия (Voilà) открывает `tools/dagbuilder_app.ipynb`, который зовёт ту же
`launch()` — обновление модулей `tools/*` обновляет и веб-приложение (после
`systemctl restart etl-dagbuilder`). См. `voila-offline/README.md`.

Рядом с полем `mode` и полем `cron` есть кнопка **ℹ** — разворачивает подробную
справку (описание всех режимов / шпаргалку по cron) прямо в форме.

### Триггеры: проверка и создание из конструктора

Линия живёт в двух местах: конфиг, структуры и даг — в репозитории, а сигнал об
изменениях даёт **триггер в БД**. Триггера два разных вида, и путать их нельзя:

| Вид | Кому | Что делает | Нет его — что будет |
|-----|------|------------|---------------------|
| **журнальный** | сложные линии в режимах `iud`, `delete_insert`, `section_compare_with_iud` | пишет строку в `etl_log_iud_row` | прогон отчитывается пропуском (⬜) и не переносит ничего |
| **аудитный** | **справочники** (`SpTableName.d`) | ставит `etl_jobs.isokaudit = 0` | даг `SpEtlNew` берёт работу ТОЛЬКО оттуда, поэтому справочник не обновится никогда — и в логах всё «хорошо» |

Раньше триггеры делали отдельно, руками по
`oracleSetup/02_trigger_template.sql` и `09_sp_audit_triggers.sql`; теперь есть
два места:

- **Блок «Триггер на ведущей»** — в форме сложной линии; у справочника свой
  блок **«Триггер справочника»** (журнального у него нет: справочник журнал не
  читает вовсе, а разовому переносу не нужен и этот — его запускают руками из
  airflow). Оба собирают DDL по форме (Oracle и Postgres, одиночный и составной
  PK, одиночный и составной период), показывают его и проверяют, что стоит в БД.
  **Выполнять DDL конструктор не умеет намеренно:** боевые триггеры заводит
  администратор БД. Вернуть кнопку — `ALLOW_TRIGGER_DDL_EXECUTION = True` в
  `tools/dag_builder_ui.py` (код выполнения цел). DDL **всегда виден в
  предпросмотре**; галочкой журнальный кладётся в репозиторий как
  `etlFolder/queries/triggers/<ключ линии>.sql` — версионируемая копия того, что
  поставлено в БД (удаляется вместе с линией).
- **Вкладка «Триггеры»** — кнопка «Проверить» проходит по всем линиям из
  `config.d` (и по справочникам) и смотрит в БД:
  - служебные объекты: журнал `etl_log_iud_row` и его колонки, `etl_jobs`,
    `etl_log`; на Oracle — ещё `etl_log_iud_row_seq` и триггер
    `trg_etl_log_iud_row_bi` (если он INVALID, ORA-04098 валит любое изменение
    любой ведущей);
  - есть ли на ведущей триггер нужного вида; включён (не DISABLED) и валиден
    (не INVALID);
  - **тот ли литерал** — сравнение с `etl_jobs.tablename` регистрозависимое,
    поэтому `'eindexmo'` вместо `'EINDEXMO'` помечается ошибкой: это молчаливый
    простой линии;
  - для справочника — есть ли в `etl_jobs` строка с его меткой: `UPDATE` по
    несуществующей строке не делает ничего, и справочник стоит;
  - полнота: INSERT, UPDATE, DELETE и `FOR EACH ROW`;
  - упоминаются ли в теле колонка периода, колонки PK и `isetl`.

  Статусы: ✅ в порядке · ⚠️ замечания · ❌ ошибка/нет триггера · 🔌 не проверено
  (нет подключения или прав) · ⬜ не требуется. Массовой кнопки «добавить/исправить
  всем» пока нет намеренно — сперва посмотреть глазами; вкладка под неё и сделана.

**Кому триггер не нужен.** `section`, `query_section` и `section_compare` журнал
не читают (группы даёт сравнение срезов, `isokaudit = 4` либо свой `periodsSql`).
Разовый перенос запускают руками — ему сигнал тоже не нужен. Журнальный блок на
вкладке справочников всё равно есть: та же таблица часто участвует ещё и в
сложной линии, и тогда триггер удобнее поставить не уходя из формы (`tablename`
должен совпадать с `tableNameEtlJobs` этой линии).

**Архивные линии не проверяются.** Линия с флагом `disabled` или с дагом в
`dags/_archived/` не работает вовсе — требовать от неё триггер незачем, это был
чистый шум в отчёте (`PODCHECK3`, `PODCHECK4`). Показать такие можно галочкой
«Показывать архивные».

**Линия на своём SELECT.** Если у линии задан `selectSql`, то `periodColumn` и
PK в конфиге — это **псевдонимы запроса**, а не колонки ведущей таблицы:
в `MOCHECK.sql` за `createdate` у TFINSCHET стоит `dschet`, а за `idrw` у
PODCHECK — `id` (и период там вообще выражение
`TO_DATE(YEAR||'-01-01','YYYY-MM-DD')`). Проверять тело триггера по псевдонимам
нельзя — получались ложные замечания «колонка CREATEDATE в теле не упоминается».
Поэтому конструктор такие линии разбирает: делит запрос на ветки `UNION`, берёт
ту, у которой ведущая стоит первой в `FROM`, и **по позиции колонки** (имена
результата UNION даёт первая ветка) находит настоящее выражение. Дальше по нему
идут и проверка, и DDL. Разбор приблизительный и честный: не нашёл — так и
пишет, колонки не проверяет и ничего не выдумывает; агрегат (`MAX(m.idrw)`)
разворачивает в колонку строки, а ссылку на присоединённую таблицу
(`mc.IDRW` из `LEFT JOIN`) отвергает — такую колонку триггер прочитать не может.
В форме линии то же самое делает кнопка **«🔎 Предположить по SQL»**. Итог всегда
показывается ДО применения DDL — сверяйте глазами.

**Справочники одной зависимости.** Даг берёт из `etl_jobs` метку (`dependence`,
по умолчанию имя ведущей без цифры на конце: `SPEINDEX1` → `SPEINDEX`) и гоняет
ВСЕ линии с такой меткой. Поэтому если по метке `SPACC` триггер стоит на
`spacc`, то линия `SPPAYCONT` (ведущие `sptf`/`spsmo`, метка та же) поедет
вместе с ней — проверка это учитывает и своего триггера от неё не требует, а
пишет, чей триггер её обслуживает.

Проверка и создание ходят в БД под набором реквизитов из `.env` (по умолчанию
`MAIN` — тем же, что рантайм). Журнал по умолчанию — тот, что читает ETL:
`koknaev.etl_log_iud_row` на Oracle, `etl_user.etl_log_iud_row` на Postgres;
переопределяется полем «Журнал».

### Расписание: как заполнять cron

Пять полей через пробел: `минута час день_месяца месяц день_недели`
(день недели: 0–6, 0 = воскресенье). Символы: `*` — любое, `,` — перечисление,
`-` — диапазон, `/` — шаг.

| Выражение | Смысл |
|-----------|-------|
| `*/5 * * * *` | каждые 5 минут |
| `0 * * * *` | каждый час в :00 |
| `50 11,13,20 * * *` | в 11:50, 13:50 и 20:50 |
| `0 3 * * *` | ежедневно в 03:00 |
| `30 2 * * 1-5` | по будням в 02:30 |
| `0 0 1 * *` | 1-го числа месяца в 00:00 |
| `0 8-18/2 * * *` | с 8 до 18 каждые 2 часа |

Одно расписание — одно выражение: «11:20 и 13:50» (разные минуты) одной строкой
не задать — либо режим «В заданные часы» (минута общая), либо два DAG'а.
Часовой пояс — как настроен Airflow (в проекте `Asia/Yekaterinburg`).

   Руками это делать больше не обязательно: конструктор собирает такой же DDL по
   форме линии, проверяет и ставит его сам — см. «Триггеры: проверка и создание
   из конструктора». Шаблон остаётся источником истины по форме триггера.

Отдельно, под `Medree_prdisp` (наполнение внутри Oracle + перенос режимом
`section`) — подробности в разделе «Medree_prdisp: процесс из двух частей»:
3. `04_medree_prdisp_idrw.sql` — sequence + BEFORE INSERT триггер для `idrw`.
4. `05_medree_prdisp_initial_fill.sql` — разовое первичное заполнение (~16 млн
   строк) **одним проходом** `INSERT /*+ APPEND */`. Помесячная нарезка здесь
   вредна: на этой БД предикат по `MEDREE.DATE_2` не driving (индекса нет),
   оптимизатор гонит от `MEDCHECK` и отбрасывает чужие месяцы уже после
   выборки — то есть каждый месяц стоит почти как весь запрос, и цикл умножает
   работу на число месяцев. `APPEND` (direct-path) почти не генерирует undo,
   поэтому один большой INSERT безопасен. Перед запуском: **удалить триггер**
   `medree_prdisp_bi`, таблица должна быть пустой (`TRUNCATE`); после — создать
   триггер заново (скрипт 04). Прогресс — `koknaev.medree_prdisp_log` и
   `v$session_longops`. Фолбэк с дроблением по годам и подсказка про индекс на
   `date_2` — в комментарии внизу файла.

Запускать 04–06 **под владельцем таблиц (`koknaev`)** — схемы в скриптах указаны
явно; роли внутри PL/SQL не действуют, поэтому под другим пользователем нужны
прямые гранты, иначе `ORA-00942`. `SET SERVEROUTPUT ON` — команда SQL\*Plus, не
SQL: в DBeaver/JDBC она даёт `ORA-00922`, там серверный вывод включается кнопкой.
Целевая версия — Oracle 11g (12c-конструкций в скриптах нет).
5. `06_medree_prdisp_daily_job.sql` — индекс по периоду, staging, процедуры

## Medree_prdisp: процесс из двух частей

Единственная линия, где список групп для переноса считает **не ETL**, а джоб
внутри самой Oracle. Стык — таблица `etl_jobs`.

| | Часть 1 — Oracle | Часть 2 — Airflow |
|-|------------------|-------------------|
| Что | пересчёт `medree_prdisp` за последние 18 мес. | перенос Oracle→Postgres |
| Чем | `koknaev.medree_prdisp_refresh` (`06_*.sql`) | даг `MedreeprdispOrclPost`, режим `section` |
| Когда | 02:00 | 05:00 и 07:00 (постановка 827, п. 8.3.1) |
| Итог | `etl_jobs.isokaudit = 4` изменившимся периодам | группа перезалита, `isokaudit = 0`, запись в `etl_log` |

Контракт стыка (нарушить — часть 2 просто ничего не увидит):
`tablename = 'MEDREE_PRDISP'` (**ВЕРХНИЙ** регистр — сравнение
регистрозависимое, значение равно `tableNameEtlJobs` из дага),
`period` = первое число месяца (`DATE`, 00:00), `isokaudit = 4`. Строку
`etl_jobs` создаёт `MERGE` внутри `medree_prdisp_mark`, заранее её заводить
не надо.

- **Гейт срабатывает 1-2 раза в месяц** (`medcheck.mekdt` за вчера), поэтому
  почти все запуски дага — пропуски (⬜). Красный/зелёный квадрат означает
  реальную работу.
- **Помечаются только реально изменившиеся периоды.** Постановка 821 говорит
  «удалить за 18 месяцев и залить заново» — буквально это ~6 млн строк
  DELETE+INSERT в Oracle, столько же в Postgres и полная перепроверка всех 18
  групп аудитом на каждом сработавшем прогоне, хотя меняются один-два свежих
  месяца. Поэтому эталон окна собирается в `medree_prdisp_stg` и сравнивается
  с текущим содержимым таблицы по полным мультимножествам —
  `(year, month, id, grouppcode)` + `COUNT(*)`, `MINUS` в обе стороны (дубли
  внутри месяца законны, их ловит `COUNT(*)`). Пропустить изменение сравнение
  не может: если период не попал в результат, буквальное «удалить и залить»
  вернуло бы ровно то же содержимое. Буквальное поведение 821 —
  `medree_prdisp_refresh(p_force => 1)`.
- **Самолечение.** Сравнение отвечает на вопрос «изменился ли Oracle», но не
  «совпадает ли Postgres». Поэтому дополнительно помечаются периоды окна, у
  которых состояние в `etl_jobs` плохое: строки нет (не переносилась), `-1`
  (перенос упал), `-2` (аудит не смог), `-4` (аудит нашёл расхождение).
  Получается замкнутый цикл: аудит нашёл `-4` → следующий прогон ставит `4` →
  часть 2 перевозит группу заново → аудит проверяет снова. Статусы `0`, `1`,
  `4` не трогаются. За пределами окна 18 месяцев цикл не работает — там
  метить руками (`medree_prdisp_mark`).
- **Данные и метка коммитятся вместе**, по периоду. Часть 2 не может увидеть
  `isokaudit = 4` на ещё не зафиксированном пересчёте.
- **Первичный перенос.** Таблица в Oracle уже залита (`05_*`), Postgres пуст.
  Режим `section` переносит только помеченное, поэтому разово выполняется
  bootstrap-блок из раздела 5 файла `06_*.sql` — он метит **все** периоды.
  ~180 групп по ~90 тыс. строк: первый прогон дага идёт часы, его можно
  прерывать (недоделанные группы остаются с `isokaudit = 4`).
- **Ведомая в Postgres** доводится скриптом
  `etlFolder/queries/postgresSetup/01_medree_prdisp_slave.sql`: индекс
  `(year, month)` обязателен — по нему идёт `DELETE` группы и выборка аудита,
  а имеющийся `(id, year, groupcode)` для этого не годится.
- **Имя колонки группы разное на сторонах**: Oracle `GROUPPCODE`, Postgres
  `GROUPCODE`. Это допустимо — стороны сопоставляются по **порядку** колонок в
  json-структурах; важно лишь, чтобы в каждом json стояло имя своей БД.

Отдельно, под линию `eindexmo` (PG → Oracle):
6. `07_eindexmo_prepare.sql` — поле `CREATEDATE` на ведомой и снятие с неё всех
   триггеров (журнал ведётся только на ведущей).

Отдельно, под даг `A61ProceduresScanLogProlong` (см. раздел ниже):
7. `08_log_eindprolong_prolong.sql` — `GRANT UPDATE` на `LOG_EINDPROLONG` для
   `etl_user` и снятие триггера журнала изменений `tr_log_eindprolong_after_iud`
   (переноса этой таблицы больше нет).

## Продление ЭИНДЕКСов: даг вместо процедуры

Линия, где Airflow не возит таблицу, а **разбирает журнал заявок на месте**:
читает Oracle, вызывает процедуру на Postgres, ответ пишет обратно в Oracle.
Отдельного конфига в `config.d` у неё нет — это не перенос.

| | Было | Стало |
|-|------|-------|
| Журнал заявок | `koknaev.LOG_EINDPROLONG` + копия на PG | только `koknaev.LOG_EINDPROLONG` |
| Кто возит | даг `LogeindprolongOrclPost` (раз в минуту) | никто, переноса нет |
| Кто разбирает | `pck_eindexmo.scanlogprolong` на PG (раз в час) | даг `A61ProceduresScanLogProlong` (раз в час) |
| Что зовётся | `pck_eindexmo.ProlongDestrEindex` внутри процедуры | она же, но из дага, параметрами из Oracle |
| Куда пишется итог | `log_eindprolong` на PG | `LOG_EINDPROLONG` на Oracle (`dwork`, `status`, `lastupdate`) |

- **Выборка та же, что была курсором процедуры** (`SelectPendingOrcl.sql`): по
  ключу МО+отдел+подразделение+подподразделение берётся одна, самая свежая по
  `timeoper` открытая заявка (`dwork is null`), порядок — по `timeoper`. Итог
  проставляется всем открытым заявкам ключа: продление применяется на текущую
  дату, поэтому более старые уже неактуальны.
- **Заявки независимы.** Упавшая получает `status = 'ERR'` и строку в
  `public.ias_func_errlog` (`idfunc = 286`, как у прежней процедуры), остальные
  разбираются дальше — это `continue` из блока `EXCEPTION`. Запуск при этом
  красный и **без авто-ретраев**: повтор нашёл бы пустой журнал (заявки уже
  закрыты как `ERR`) и перекрасил 🟥 в 🟪, спрятав ошибку.
- **Задача живёт в пуле `Etl`**, поэтому на время аудита (замок `etl_lock`
  занимает весь пул) не стартует: процедура правит `public.eindexmo` — ведущую
  таблицу линии `eindexmo` PG → Oracle.
- **Права и триггер на Oracle** — `oracleSetup/08_log_eindprolong_prolong.sql`:
  нужен `UPDATE` на журнал, а триггер `tr_log_eindprolong_after_iud` надо снять,
  иначе он продолжит копить в `etl_log_iud_row` строки, которые никто не
  разбирает (даг своими `UPDATE`'ами их ещё и добавит).
- **Что можно убрать на PG** — памятка в
  `postgresSetup/02_log_eindprolong_retire.sql`: сама `pck_eindexmo.scanlogprolong`
  и остановившаяся копия `log_eindprolong`. Обязательным это не является.

## Установка на PostgreSQL

Запустить из `etlFolder/queries/postgresSetup/`:
1. `01_eindexmo_etl_setup.sql` — поле `createdate` на ведущей `eindexmo`,
   перенос в него `lastupdate::date`, `BEFORE INSERT` триггер на заполнение
   `createdate` и `AFTER INSERT/UPDATE/DELETE` триггер, пишущий `IU`/`D` в
   `etl_user.etl_log_iud_row`.
2. `02_log_eindprolong_retire.sql` — **не установка, а памятка**: что осталось
   ненужным после перевода продления ЭИНДЕКСов на даг (см. раздел «Продление
   ЭИНДЕКСов: даг вместо процедуры»). Выполнять руками и только при желании.

Общая схема для любой ведущей на PG та же, что и на Oracle
(`oracleSetup/02_trigger_template.sql`), с поправками PL/pgSQL: NEW меняется
только в `BEFORE`-триггере, поэтому заполнение периода и логирование — это два
разных триггера; функция логирования объявляется `SECURITY DEFINER`, чтобы
прикладным пользователям не нужны были права на `etl_user.etl_log_iud_row`.
Скрипт заодно снимает вопрос смены ключа/периода: при `UPDATE`, меняющем
`idrw` или `createdate`, в журнал дополнительно уходит `D` по старой паре.

## Гейт выкладки: почему битый код больше не уезжает

Проверка **встроена в сами команды выкладки** — отдельно запускать нечего и
незачем забывать:

| Когда | Кто зовёт | Что делает провал |
|-------|-----------|-------------------|
| `bash local/dev-push.sh` | до обоих `git push` | push не начинается |
| `bash deploy/deploy-prod.sh` | до вопроса «Выкладываем на ПРОД?» | выкладка отменяется |
| `git push` на сервер (любой, хоть руками) | `pre-receive` в bare-репо | **push отклонён**, на сервер ничего не легло |
| после выкладки | `post-receive` | сервисы не рестартуют (страховка, не гейт) |

Проверяет `deploy/check-dags.sh` → `tools/check_dags.py`, три яруса:
**синтаксис** (`compile()` каждого `.py`), **конфиг** (сборка фрагментов
`config.d/` — битый json и дубль ключа парсингом дагов не ловятся, `lineEnabled`
их намеренно глушит) и **парсинг DAG'ов** (настоящий `DagBag`).

**Airflow-сервер для этого поднимать не нужно.** `DagBag` — библиотечный разбор
файлов; нужен только импортируемый пакет `airflow`. Скрипт сам подбирает
интерпретатор (перенесённый на dev-PC runtime, `/opt/airflow/venv` на сервере;
переопределяется `ETL_CHECK_PYTHON`) и строит себе окружение: временный
`AIRFLOW_HOME`, sqlite-заглушка вместо metadata-базы, каталог дагов передаётся в
`DagBag` **явно** — чтобы «OK» означало «проверено вот это дерево».

Коды возврата: `0` прошло, `1` ошибки, `2` прошло частично (нет `airflow`, даги
не парсились). На сервере гейт зовётся с `REQUIRE_AIRFLOW=1`, где `2`
превращается в отказ — гейт падает **закрыто**.

Единственное послабление — **откат**. Если в присланном дереве нет
`deploy/check-dags.sh` (старый тег `prod-*`, где проверки ещё не было),
`pre-receive` не отклоняет push вслепую, а прогоняет встроенный минимум —
`python3 -m compileall`. Откат обязан работать всегда, тем более в аварии; но и
сломанный синтаксис так не проедет.

Обойти клиентскую проверку осознанно: `SKIP_CHECKS=1 bash local/dev-push.sh`.
Серверный `pre-receive` этим не обходится — в том и смысл.

### Почему гейт именно в `pre-receive`

До 2026-08-07 проверка жила только в `post-receive` и не защищала ни от чего:

* она шла **после** `git checkout -f` в `$SRC`, то есть код уже лежал в
  `DAGS_FOLDER`, который scheduler перечитывает сам. «Сервисы не перезапущены,
  прод работает как работал» было неправдой — прод падал независимо от рестарта;
* её код возврата git **игнорирует**, а `dev-push.sh`/`deploy-prod.sh` смотрят
  только на код `git push` — поэтому оба печатали «Готово» на провалившейся
  проверке;
* обёрток было **две** (свои heredoc'и в `setup-airflow-test.sh` и
  `setup-airflow-prod.sh`), и они разъехались: тест сказал «OK» на коде, который
  прод не смог распарсить, и прод лёг.

`pre-receive` работает по временной распаковке присланного коммита
(`git archive` — объекты видны из карантина ещё до обновления ссылок): провал →
ссылки не двинулись, рабочее дерево не тронуто, ненулевой код виден клиенту.
Серверных копий проверки больше нет — обе стороны зовут один скрипт из
репозитория.

Хуки ставятся `setup-airflow-test.sh` / `setup-airflow-prod.sh` (оба
идемпотентны) — после обновления этих скриптов их надо **перезапустить на
сервере**, иначе на нём останутся старые хуки.

## Переменные окружения

Хранятся в файле `.env` в корне проекта (он в `.gitignore`, в репозиторий
не уходит). Шаблон со всеми ключами и значениями-плейсхолдерами —
`.env.example`.

Подготовка: `cp .env.example .env` и подставить свои значения. На старте
любого модуля (`Connect/__init__.py`, `Src/fullPath.py`) автоматически
вызывается `python-dotenv`, который и подхватит `.env`. Если переменная
уже задана в системе (`export ...`), она имеет приоритет — `.env` не
перетирает то, что уже есть.

Список ключей — в `.env.example`:

```
ETL_FULL_PATH, ETL_MODE
ETL_ORACLE_HOST / PORT / SID / USER / PWD / CONFIG_DIR
ETL_POST_HOST / PORT / DB / USER / PWD
```
