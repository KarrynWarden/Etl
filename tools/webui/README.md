# Веб-интерфейс конструктора ETL-линий

Замена интерфейсу на ipywidgets/Voilà. React 18 + Ant Design 5, собирается Vite 4.

Логика конструктора не тронута: интерфейс ходит в `tools/dagbuilder_api.py`,
который тонким слоем лежит поверх `tools/dag_builder.py` и
`tools/trigger_builder.py`. Отсюда следует, что все самопроверки этих модулей
продолжают страховать переезд, а `dagbuilder_api.py --selftest` проверяет
маршруты без сети и без БД.

## Почему версии прибиты гвоздями

```
vite 4.5.5   — Vite 5+ тянет Rollup 4, а тот перешёл на НАТИВНЫЕ бинарники под
               Windows 8+. Сборочная машина — Windows 7, и rollup 4 падает там с
               ERR_DLOPEN_FAILED («указанная процедура не найдена»). Rollup 3
               внутри Vite 4 — чистый JavaScript.
react 18     — с React 19 у AntD 5 нужен пакет-прослойка
               @ant-design/v5-patch-for-react-19. Для внутреннего инструмента
               это лишняя зависимость без единого плюса.
node 18      — последняя ветка, которая работает на Windows 7.
```

`package-lock.json` лежит в репозитории намеренно: сборка через полгода должна
дать то же самое, что проверяли сегодня.

## Сборка (машина с интернетом)

```
cd tools/webui
npm ci          # строго по package-lock.json
npm run build   # -> tools/webui/dist
```

Если npm не видит сеть — дело обычно в прокси. Проверить: `npm config get
https-proxy`. У pip на той же машине бывает своя беда: он берёт прокси из
РЕЕСТРА Windows и превращает его в `https://…`, после чего падает с
`check_hostname requires server_hostname`. Лечится явной переменной со схемой
`http://`:

```powershell
$env:HTTPS_PROXY = "http://<host>:<port>"
```

## Разработка

Нужны два процесса:

```
python3 tools/dagbuilder_api.py --port 8085     # API
cd tools/webui && npm run dev                   # интерфейс на 5173
```

Запросы `/api/*` из режима разработки проксируются на 8085 (см.
`vite.config.js`), поэтому адрес API в коде не зашит.

## Установка на сервер

Собранный `dist` попадает на сервер вместе с репозиторием — **node и npm на
сервере не нужны вовсе**. Раздаёт его сам `dagbuilder_api.py` (tornado, уже
стоит в окружении JupyterLab), так что отдельный веб-сервер тоже не нужен:

```
/opt/jupyter/bin/python tools/dagbuilder_api.py --port 8085
```

Слушает `127.0.0.1` — наружу отдаёт Apache, как сейчас Voilà. Конструктор пишет
файлы в репозиторий, делает `git push` и ходит в боевые БД, поэтому открывать
его на все интерфейсы (`--host 0.0.0.0`) без авторизации перед ним нельзя.

`base: './'` в конфиге Vite — чтобы приложение работало на подпути
(`https://<домен>/dagbuilder/`), а не только в корне.

## Что уже сделано

**Линии.** Список с четырьмя складывающимися фильтрами — поиск по имени линии и
таблиц, направление, режим, теги дага, плюс переключатель «в работе / в архиве».
Фильтры не украшение: линий три десятка, и поиск по имени работает, только пока
имя помнишь.

**Правка линии** — всё, что умел прежний конструктор, по вкладкам:

- *Настройки*: таблицы (с кнопкой приведения регистра, см. ниже), режим, обе
  колонки периода, `filterClause` и
  `filterClauseSlave`, `conflictExtra` и `conflictWhere`, `truncatePeriod`,
  `_doc`, а также флаги `disabled` и `skipAudit`. `auditExcludeFields` —
  выпадающий список колонок ведущей, а не поле для набора имён по памяти;
- *Колонки*: **правка** сопоставления, а не только просмотр. Каждой колонке
  ведущей выбирается пара из ведомой, правятся имя, тип и `scale` обеих сторон,
  ставится признак PK, добавляются и убираются колонки. Фильтр «все / с парой /
  без пары» — на полсотни колонок это разница между «нашёл» и «искал».
  Позиции показаны намеренно — перенос пишет строку ПО ПОЗИЦИЯМ структур, а не
  по именам, поэтому пара с разными именами (`GROUPPCODE` / `groupcode`) это
  норма, а сдвиг на строку — беда. Колонки без пары, расхождение признака PK,
  дважды занятая колонка ведомой и колонки ведомой, которые ETL не заполняет,
  показаны отдельными предупреждениями.

  Имя колонки ведущей правится прямо в строке: поменяли псевдоним в SELECT —
  меняете его же в структуре, за один заход и один коммит.

  Колонка ведомой предлагается только СВОБОДНАЯ (занятые чужими парами скрыты,
  открываются галочкой): одна колонка ведущей в две колонки ведомой — случай
  редкий и обычно решается псевдонимом в запросе, а вот занять чужую пару из
  общего списка легко — имена похожи, строк полсотни;
- *Колонки → «Снять структуры из БД»*: снятие **ничего не меняет само**. Оно
  показывает список отличий — новая колонка, пропавшая колонка, другой тип,
  другой признак ключа — и каждое принимается или отклоняется отдельно; не
  тронутое считается отклонённым. Сопоставление при этом не пересобирается
  вовсе: пары, расставленные руками, остаются как есть.

  Так и должно быть. Прежний вариант заменял обе стороны и подбирал пары заново
  по именам, а нажимают эту кнопку обычно ради одной новой колонки. В `prbdir`
  ключи зовутся `idrw` и `prvdirid` — автоподбор такую пару не восстановит. Ещё
  хуже случай `acc` → `bancacc`, когда в ведомой есть и `bancacc`, и свой `acc`:
  автоподбор уверенно свяжет `acc` с `acc` и молча испортит перенос.

  Ведущая снимается **по тексту SELECT из формы**, а не по тому, что лежит в
  файле: правка запроса и правка структуры — одна работа, и делить её на два
  круга «сохрани → сними → сохрани» незачем;
- *Даг и расписание*: свой даг или составной, `dag_id`, интервал либо cron,
  режим ретраев, теги;
- *SQL*: текст `selectSql`; поле «SQL периодов» показывается только в режиме
  `query_section` — читает его ровно этот режим, и у остальных линий пустое
  поле выглядело недоделанной настройкой;
- *Действия*: архив и восстановление, удаление насовсем — со списком того, что
  будет снесено, до подтверждения.

## Регистр имени таблицы

У каждого поля с именем таблицы — своя кнопка приведения регистра к диалекту
той БД, которой это поле принадлежит: Oracle — ВЕРХНИЙ, Postgres — нижний.
Ввели в ведущую Oracle `koknaev.iprkdept` — кнопка станет активной и предложит
`KOKNAEV.IPRKDEPT`, под полем будет видно, что именно получится. Кнопка есть в
правке линии, в новой линии и в справочниках, на обеих сторонах.

Кнопка, а не правка на лету, — намеренно: имя набирают, вставляют из буфера,
правят по частям, и поле, переписывающее набранное на каждой букве, отбирает
управление ровно тогда, когда оно нужнее всего.

Значения, пришедшие с диска, сами не меняются. У восемнадцати линий
справочников ведомая записана не тем регистром (`KOKNAEV.spacc`, `Spvmpserv`) и
прекрасно работает — для неэкранированных имён обе БД регистр игнорируют.
Перебей их при открытии формы — и предпросмотр показал бы правку, которой никто
не делал. Поэтому расхождение только показывается, а решает человек.

Регистр всё же важен, хотя БД его и игнорируют: из имени таблицы складываются
имя линии (`tableNameEtlJobs`) и пути структур, а имя линии сравнивается с
`etl_jobs.tablename` **дословно**. Ошибка здесь — это «Конфиг для ключа … не
найден» при переносе и молчаливый ноль групп в аудите.

Правило одно на обе стороны: `dag_builder.to_db_case` и
`tools/webui/src/dbCase.js`. Регистр меняется по каждой части через точку
(схема и имя отдельно), содержимое кавычек не трогается — в них регистр значим.
Набор проверочных случаев общий, самопроверка следит, чтобы правило в JS не
разъехалось с питоновским.

## На диск — только по кнопке

**Ни одно действие не меняет репозиторий раньше, чем вы нажмёте «Записать».**

Закончить работу можно тремя способами — как и в прежнем конструкторе:
«Записать», «Записать и запушить» (одним действием, но запись первой: пушить
неудавшуюся запись нечего) и отдельная кнопка в шапке, которая коммитит и
отправляет всё незакоммиченное в клоне, включая записанное раньше.

Исключений ровно три вида, и каждое спрашивает подтверждение со списком того,
что произойдёт: **запись** (она и есть кнопка), **перемещение и удаление
файлов** (архив, восстановление, удаление линии, перевод справочника между
типами — собрать это в предпросмотр нечем) и **git push**.

Так было не всегда. Флаги `disabled` и `skipAudit` переключались тумблером,
который писал конфиг сразу по щелчку: задел мышью, не заметил, перезагрузил
страницу — а линия уже отключена в репозитории, и узнать об этом можно было
только из `git diff`. Теперь оба флага — обычные поля формы: они собираются
вместе с конфигом, видны в предпросмотре как изменение файла и попадают на диск
той же кнопкой, что и всё остальное. Маршруты `set-flag` и `sp/set-disabled`
удалены, а самопроверка держит закрытый список пишущих маршрутов — новый
придётся вписать туда руками, и это как раз тот момент, когда стоит спросить
себя, почему он не идёт через предпросмотр.

**Кнопка «Отменить»** возвращает форму к тому, что лежит на диске. Пока правки
только в форме, об этом сказано прямо — на диск они попадают лишь через
предпросмотр и запись.

**Предпросмотр** показывает, какие файлы **изменятся**, какие будут **созданы** и
какие останутся как были. У изменяемого файла показывается не новый текст
целиком, а построчная разница, как в git: убранное красным, добавленное зелёным,
длинные куски без изменений свёрнуты. Для дага в двести строк это разница между
«вижу правку» и «вычитываю глазами». Запись и `git push` — оттуда же и из шапки.

У каждого изменяемого файла своя галочка, и записывается только отмеченное.
Нужно это из-за дагов: часть из них писана руками, и пересборка приводит их к
шаблону — убирает неиспользуемые импорты, меняет кавычки в `tags`, переписывает
первую строку docstring. Всё это безобидно, но если правил ты только период,
видеть в списке переписанный даг незачем — снял галочку, и файл остался как был.

Что пересборка **не** трогает: `dag_id` и имя задачи (`do_etl_…`) берутся из
самого файла, а не выводятся из имени линии — на них висит вся история запусков
в Airflow, и переименование завело бы новую задачу вместо продолжения старой.
Путь файла дага тоже сохраняется: `dags/IpersonOrclPost.py` объявляет
`dag_id="IpersonPostOrcl"`, и вывод пути из `dag_id` создал бы второй файл с тем
же `dag_id` — такую пару Airflow не берёт вовсе. Ключи-умолчания (`mode`,
`tableNameMaster`) появляются в конфиге, только если они там уже были, а ключи,
которых форма не знает — `disabled` в первую очередь — проходят насквозь.

**Новая линия** — кнопка «+ Создать» над списком линий, на той же вкладке.
Отдельной вкладки наверху нет намеренно: раньше у сложного ETL «Линии» и «Новая
линия» были разными вкладками, а у справочников создание и правка — одной, и
одинаковые по смыслу вещи выглядели устроенными по-разному. Теперь везде
одинаково: слева список с кнопкой «+ Создать», справа форма.

Создание идёт по шагам: снять структуры из БД (таблица или свой SELECT) →
сопоставление колонок с автоподбором и ручной правкой каждой пары → даг и
запись. Шаги разделены потому, что снятие структур ходит в БД и занимает
секунды, а сопоставлять есть что только после него.

**Триггеры** — кому нужен, какие колонки ведущей за этим стоят, что реально
стоит в БД (сверка) и готовый DDL для передачи администратору. Выполнять DDL в
боевой БД конструктор по-прежнему не умеет намеренно.

После сверки строки выстраиваются по СРОЧНОСТИ: сначала «стоит неправильно»
(молчит и врёт — хуже всего), потом «триггера нет», «проверить не удалось», и
только в конце совпавшие; их можно и вовсе скрыть галочкой. Список триггеров —
это список дел, а не алфавитный указатель. Сверка при этом всегда идёт по всем
подходящим линиям, а не по видимым, иначе починенное перестало бы
перепроверяться.

Результат показывается по-русски («стоит и совпадает», «триггера нет», «стоит
неправильно») вместе с перечнем расхождений, а отдельным блоком — отчёт
по каждой БД. Он важнее, чем кажется: самая частая причина «все линии красные» —
это не триггеры, а «подключиться не удалось», и без такого блока сверка
выглядела бы приговором всем линиям сразу.

**Ошибка каждого действия показывается РЯДОМ с этим действием.**

Последний пункт — причина переезда. В ноутбуке ошибка уходила текстом в общую
консоль внизу страницы, и после «Снять структуры из БД» её можно было просто не
заметить. Здесь у каждого действия своё состояние (`useAction`) и своё место для
ошибки (`ActionError`), а вид ошибки различается: не хватает данных в форме,
не отвечает сервис или упала логика конструктора — это три разные проблемы с
тремя разными адресатами.

**Справочники и разовый перенос** — отдельная вкладка со своим набором
понятий. Список обоих типов с фильтрами по имени и по участию в работе,
**создание новой линии**, правка (таблицы, `dependence`, режим источника,
`append` у разового, `_doc`), сопоставление колонок, тексты Select.sql и
Add.sql, включение и отключение, перевод между типами, удаление и DDL
**аудитного** триггера — того, что ставит `isokaudit = 0`, то есть подаёт дагу
сигнал «перенеси справочник».

Создание — кнопка «+ Создать» над списком; тип берётся из того переключателя,
на котором вы стоите. Поля у создания и правки одни и те же, отличается только
откуда взялись начальные значения — так же устроены и линии сложного ETL.
Порядок: заполнить обе таблицы и метку линии → «Колонки» → «Снять колонки из
БД» (пары подбираются по именам, расставленное руками не трогается) →
«Предпросмотр» → «Записать». Ключ фрагмента складывается из метки и пары БД и
показан в заголовке заранее; если он уже занят, форма скажет об этом до
предпросмотра, а не отказом при записи. Регулярному справочнику после создания
нужен ещё **аудитный триггер** — без него он не обновится ни разу и ошибки при
этом не выдаст; DDL берётся на вкладке «Действия».

Колонки правятся так же, как у сложного ETL: переименование ведущей и ведомой
прямо в строке, приведение регистра всех имён одной кнопкой, фильтр «все / с
парой / без пары», запрет занять колонку ведомой, уже отданную другой паре
(снимается галочкой), предупреждения о дважды занятой и о незаполняемых
колонках. Разные страницы одного конструктора не должны вести себя по-разному.

Отличие от сложного ETL одно: у колонок справочника **нет типов**. Линия описана
парой готовых SQL, и всё, что о колонках известно, — их имена из SELECT и из
INSERT.

**Колонки и SQL связаны в обе стороны.** Правка сопоставления пересобирает
запросы, правка запроса (по уходу из поля) пересобирает колонки. Так и должно
быть: линия ОПИСАНА этими двумя файлами, значит колонки и SQL — два взгляда на
одно и то же, а не «настоящее» и «только для чтения». Собирает и разбирает
сервер теми же функциями, что пишут файлы (`build_sp_select` / `build_sp_add` /
`restore_mapping`), — повтори их в браузере, и текст в форме разошёлся бы с
текстом в файле на первом же пробеле.

Раскладка рукописного SQL при этом не трогается, пока состав колонок тот же: у
`SPMKB` все семнадцать колонок в одну строку, а генератор ставит перенос после
каждой — без этой оговорки выбор пары у одной колонки переписывал бы весь
запрос ради переносов строк.

**Колонки и свой SELECT — не два варианта конструктора.** Это инструменты,
работающие вместе, и переключателя «в каком я варианте» перед работой нет.
Снятие колонок спрашивает только одно — откуда их взять ЭТОТ раз:

| кнопка | откуда колонки | зачем |
|---|---|---|
| «Снять по таблице» | `all_tab_columns` / `information_schema` ведущей | видны и колонки, появившиеся в таблице недавно; из них собирается `SELECT c1, c2 FROM t` |
| «Снять по запросу» | описание курсора **вашего** запроса | имена — псевдонимы запроса, ровно как их увидит рантайм; масштаб и признак ключа подмешиваются из таблицы |

Написали свой запрос и нажали «Снять по запросу» — колонки разберутся из него и
пары подберутся по именам; запрос после этого принадлежит вам и не
пересобирается. Нажали «Снять по таблице» — наоборот, запрос соберётся из
колонок. То есть режим не выбирают заранее, он **следствие** последнего
действия; текущее состояние видно на «Настройках» и на вкладке SQL, и там же
меняется одной кнопкой, без снятия.

Раньше кнопка снятия молча смотрела на режим линии и написанный руками SELECT
игнорировала, пока режим не переключат отдельно, — то есть требовала объявить
свой «вариант», прежде чем сделать очевидное.

Был и третий — «вся таблица»: без файла Select.sql, рантайм подставлял
`SELECT * FROM ведущей` (`dags/SpDagNew.py`, `dags/SpOnce.py`), так заведён
CALENDAR. Из выбора он убран. Смысл у него был, пока конфиг и SQL правились
руками: не перечислять колонки — экономия. Теперь колонки снимаются кнопкой,
зато явный список ловит расхождение структур ДО переноса, а `SELECT *`
сопоставляет по позиции и ломается молча, стоит кому-нибудь добавить колонку в
ведущую. Линии, оставшиеся в этом режиме, читаются по-прежнему, и им предлагается
кнопка «Снять колонки из БД и перевести».

## Чего ещё нет

Всё, что умел прежний конструктор, перенесено.

## Если страница открылась ПУСТОЙ

Белый экран без единого сообщения — это почти всегда не сервис. Два источника:

1. **index.html и assets/ разъехались.** Имя собранного файла содержит хэш
   содержимого (`index-8dd06153.js`) и меняется при каждой пересборке. Стоит
   перенести на сервер один файл без другого — браузер просит старый `.js`,
   а получает… раньше получал index.html со статусом 200, не мог его исполнить и
   оставлял страницу пустой. Теперь такой запрос честно отдаёт 404 (видно в
   консоли браузера), а сервер вдобавок проверяет целостность `dist` при старте
   и пишет в лог `ФРОНТЕНД: index.html ссылается на …, а файла нет`. Лечится
   пересборкой или переносом каталога `tools/webui/dist` целиком.
2. **Исключение при отрисовке.** React снимает всё дерево, и окно белеет.
   Теперь это перехватывается (`ErrorBoundary`) и показывается текстом ошибки со
   стеком и кнопкой перезагрузки — данные на диске при этом не трогаются, до
   записи дело не доходит.

## Проверка контракта

Интерфейс собирается отдельно и на другой машине, поэтому опечатка в имени
маршрута сборкой не ловится: она проходит, а в браузере кнопка молча получает
404. Поэтому `tools/dagbuilder_api.py --selftest` вычитывает имена маршрутов
прямо из `src/api.js` и требует, чтобы каждый существовал на сервере.
