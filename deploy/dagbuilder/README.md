# Постоянная установка веб-конструктора ETL-линий

Сейчас конструктор живёт, пока открыт ssh: на сервере руками запускается
`dagbuilder_api.py`, на своей машине — `ssh -L`. Так работать может только тот,
у кого есть ssh-доступ и ключ, а сервис умирает вместе с сессией.

Здесь — как сделать его постоянным: **systemd** (живёт сам, поднимается после
перезагрузки) + **Apache** (адрес, https, авторизация).

**Сисадмины для этого не нужны.** Оба шага делаются своими силами, нужен только
root на сервере: имя `airflow-test.oms66.ru` и сертификат к нему уже есть,
добавляется лишь путь.

```
браузер коллеги
   │  https://airflow-test.oms66.ru/etl_builder/     ← имя и сертификат уже есть
   ▼
Apache (сервер, :443) ──proxy──► 127.0.0.1:8085 ──► dagbuilder_api.py (systemd)
                                                        │
                                        рабочий клон /opt/jupyter/workdir/…/etl
```

Отдельный домен (`dagbuilder.oms66.ru`) — вариант Б ниже; вот он уже требует
заявки в DNS, и нужен, только если подпуть чем-то не устроит.

## Шаг 1. Сервис

```bash
ssh devel@airflow
sudo bash /opt/jupyter/workdir/konkin/etl/deploy/dagbuilder/install.sh
```

Скрипт сначала проверяет предпосылки и **ничего не ставит, если что-то не так**:

| проверка | почему именно она |
|---|---|
| собранный `dist` цел | разъехавшиеся `index.html` и `assets/` дают ПУСТУЮ белую страницу без единого сообщения — выглядит как «сервис не работает» |
| `--selftest` проходит | ловит и битый конфиг в самом репозитории, до того как это увидит человек |
| `git push` из-под `jupyter` | иначе «Записать и запушить» упадёт в проде, у того, кто к настройке отношения не имеет |
| порт 8085 свободен | 8080–8084 уже заняты (airflow, jupyter, airflow-test, gunicorn, Voilà) |

После установки сервис слушает `127.0.0.1:8085` и переживает перезагрузку.
Проверить, не дожидаясь Apache:

```bash
systemctl status etl-dagbuilder-api --no-pager
journalctl -u etl-dagbuilder-api -n 50
ssh -L 18085:127.0.0.1:8085 devel@airflow    # → http://localhost:18085/
```

## Шаг 2. Адрес

### А. Подпуть на существующем домене — сисадмины НЕ нужны

**`https://airflow-test.oms66.ru/etl_builder/`** — ни заявки в DNS, ни нового
сертификата: имя и сертификат уже есть, добавляется только путь. Нужен лишь
root на самом сервере.

```bash
sudo bash deploy/dagbuilder/install-apache-subpath.sh
```

Скрипт сам находит включённый vhost по `ServerName`, включает нужные модули,
заводит файл паролей (спросит имя первого пользователя), вставляет блок и
проверяет результат. Что он делает аккуратно, а не «как получится»:

* **копия vhost до правки**, и если `apache2ctl configtest` не прошёл — конфиг
  возвращается из копии, ничего не меняется;
* **блок вставляется ПЕРЕД общим `ProxyPass /`**. Apache берёт первое подходящее
  правило, а `/` подходит под всё — вставь ниже, и путь уедет в airflow;
* **повторный запуск заменяет свой блок** (он помечен маркерами) и не трогает
  чужого — конфиг не обрастает копиями;
* в конце проверяет реальный адрес: 401 — Apache просит логин, значит всё
  собралось; 503 — Apache настроен, но сервис лежит.

Параметры, если что-то называется иначе:

```bash
sudo VHOST=/etc/apache2/sites-available/мой.conf URLPATH=/etl_builder \
     PORT=8085 AUTH_USER=konkin bash deploy/dagbuilder/install-apache-subpath.sh
```

Одна тонкость, ради которой в конфиге стоит редирект: адрес API и пути к файлам
сборки приложение считает от `document.baseURI`. Открытый без завершающего
слэша `/etl_builder` даёт базой корень сайта — запросы уходят в `/api/`, то есть
в airflow, а скрипты в `/assets/`, где их нет; страница открывается **пустой**.
Редирект `^/etl_builder$ → /etl_builder/` снимает весь этот класс жалоб разом.

Откатить всё:

```bash
sudo cp -a /etc/apache2/sites-available/<vhost>.bak-<дата> /etc/apache2/sites-available/<vhost>
sudo systemctl reload apache2
```

### Б. Свой домен — вот тут уже нужна заявка

`https://dagbuilder.oms66.ru/` — понятный адрес, отдельные логи, отдельный
доступ. Конфиг: `apache-dagbuilder-vhost.conf.example`. Нужно только если
вариант А чем-то не устроит: подпуть работает ровно так же.

## Что попросить у сисадминов (текст заявки)

> Прошу завести DNS-запись для внутреннего инструмента:
>
> * **Имя:** `dagbuilder.oms66.ru`
> * **Тип:** `A` (или `CNAME` на имя сервера airflow)
> * **Значение:** IP того же сервера, на котором работает `airflow-test.oms66.ru`
> * **Зона:** внутренняя, наружу публиковать не нужно
>
> Сертификат, скорее всего, уже есть: `airflow-test.oms66.ru` обслуживается
> сертификатом `/etc/ssl/certs/oms66.crt`. Если он выписан на `*.oms66.ru`, то
> новое имя он покрывает и выпускать ничего не нужно. Проверить:
>
> ```bash
> openssl x509 -noout -text -in /etc/ssl/certs/oms66.crt | grep -A1 'Subject Alternative Name'
> ```
>
> Если сертификат выписан на одно имя — прошу перевыпустить с добавлением
> `dagbuilder.oms66.ru` в SAN либо выдать отдельный.
>
> Конфигурацию Apache подготовили сами:
> `deploy/dagbuilder/apache-dagbuilder-vhost.conf.example` в репозитории ETL.
> Ставится в `/etc/apache2/sites-available/`, нужны модули `proxy`,
> `proxy_http`, `headers`, `auth_basic`, `authn_file`, `authz_user`.
>
> Сетевой доступ: тот же, что у `airflow-test.oms66.ru` — 443/tcp из рабочей
> сети. Новых правил на межсетевом экране не требуется, если инструмент живёт
> на том же сервере.
>
> Доступ к инструменту закрываем Basic-авторизацией (файл
> `/etc/apache2/dagbuilder.htpasswd`). **Если в организации есть LDAP** —
> подскажите параметры, подключим к нему: список людей будет вестись в одном
> месте, а не отдельным файлом на сервере.

Короткая версия, если нужно одной строкой: **A-запись `dagbuilder.oms66.ru` на
IP сервера airflow; подтвердить, покрывает ли текущий сертификат это имя; при
наличии LDAP — дать параметры подключения.**

## Про авторизацию — отдельно и всерьёз

Своей авторизации у конструктора **нет вовсе**. Он пишет файлы в репозиторий,
делает `git push` и ходит в боевые БД под их реквизитами. Вся защита — Apache
перед ним.

Отсюда два правила, и оба не декоративные:

1. Сервис слушает `127.0.0.1`. Не `0.0.0.0`. Иначе он доступен всем, кто
   доберётся до порта, минуя Apache со всей его авторизацией.
2. Vhost или `<Location>` закрыт `Require valid-user`. Своя форма входа у
   airflow конструктор **не** закрывает — это разные приложения на одном
   сервере.

Завести пользователей:

```bash
sudo htpasswd -c /etc/apache2/etl_builder.htpasswd konkin   # -c только для первого
sudo htpasswd    /etc/apache2/etl_builder.htpasswd ivanov
```

## Обновление после правок в интерфейсе

Собранный `dist` лежит в репозитории, поэтому на сервере ни node, ни npm не
нужны:

```bash
cd /opt/jupyter/workdir/konkin/etl
git pull
sudo systemctl restart etl-dagbuilder-api
```

Перезапуск нужен только питоновской части (маршруты API). Правки фронтенда
подхватываются сами — их отдаёт статикой тот же процесс, но браузер держит
файлы в кэше, поэтому после обновления имеет смысл открыть страницу с
Ctrl+F5.

## Если что-то не так

| симптом | где смотреть |
|---|---|
| страница пустая, белая | сначала консоль браузера: 404 на `assets/…js` = `dist` неполный или разъехался. Затем `journalctl -u etl-dagbuilder-api` — при старте сервис сам пишет `ФРОНТЕНД: …` |
| 503 от Apache | сервис лежит: `systemctl status etl-dagbuilder-api` |
| страница есть, кнопки молчат | открыли адрес без завершающего слэша: нужен `/etl_builder/`, а не `/etl_builder` (редирект ставит скрипт) |
| «нет связи с сервисом конструктора» | Apache проксирует не туда: проверьте порт в `ProxyPass` и `ss -ltnp | grep 8085` |
| кнопка «запушить» падает | `sudo -u jupyter git -C <репо> push --dry-run` |
| «не нашёл включённый vhost» | скрипт печатает всю карту `apache2ctl -S` — посмотрите, под каким именем сайт там записан, и запустите с `SERVER_NAME='<это имя>'` или `VHOST=/путь/к/файлу.conf`. Если имени нет вовсе — сайт отдаёт другая машина: `getent hosts <имя>` и `hostname -I` |
